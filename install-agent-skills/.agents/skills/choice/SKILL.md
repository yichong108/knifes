# Choice

帮助用户看清选择：先摸清谁受损谁受益、立场与资源，再谈有哪些路、各路利害、哪里有坑——**不替用户拍板**。

## 何时必须启用

出现以下任一信号时启用本 skill，即使未被点名：

- 可能造成**金钱损失**、锁仓、扣费、违约金、订阅陷阱
- 可能造成**数据丢失/泄露**、权限扩大、密钥暴露、账号接管
- **不可逆或难逆**操作（删库、force push、覆盖生产、迁移、注销）
- 可能损害**声誉、合规、法律、就业或人身安全**相关利益
- 用户在「要不要做 / 选 A 还是 B / 风险大不大」上犹豫

## 两阶段铁律

1. **阶段一（探询）**：用对话逐个提问，摸清利益方、立场、背景与资源；**不要**列出方案对比、默认推荐或可执行步骤。
2. **阶段二（方案）**：仅在用户对探询摘要**明确确认**（或补齐关键答案）后，再输出方案与利害。
3. 用户未确认前若催促「直接给方案」：简短说明缺什么会歪曲利害，继续用**一个**必要问题推进；不得跳过确认。

信息不足时，用模糊建议掩盖利害，或凭猜测堆方案，均禁止。

## Workflow

### 阶段一：多方探询 → 等确认

- [ ] 识别相关**利益方**（谁受益 / 谁承担风险 / 谁可能被连累）
- [ ] 从不同**立场与角度**探询（决策者、执行者、受影响方、合规/安全、时间与成本等）
- [ ] 摸清**背景与资源**（权限、备份、预算、期限、依赖、已发生事实）
- [ ] **每轮只问 1 个问题**，等用户回答后再问下一个；禁止一次甩出问题清单
- [ ] 关键缺口基本齐后，汇总「我理解的利害与约束」，请用户确认或纠正
- [ ] **停下**：等用户确认后再进入阶段二

### 阶段二：方案与利害（确认后）

- [ ] 列出 2–4 个真实可选方案（含「暂缓 / 不作为」若合理）
- [ ] 对每个方案写清：收益、代价、触发条件、退出成本
- [ ] 对每条利害补一句「为何会出现」（机制/因果，通俗易懂）
- [ ] 按风险级别标注坑点
- [ ] 给出默认推荐 + 适用前提；声明最终由用户决定
- [ ] 交付「若选 X，下一步怎么做」的可执行路径；危险操作仍须用户选定后再执行

## 阶段一：逐问对话规则（必须）

探询是**一问一答的对话**，不是问卷。

1. **每轮只问 1 个问题**（可附极短说明：为何问这个）。禁止同轮抛出 2 个及以上问题，禁止按「利益方 / 立场 / 资源」分组列清单。
2. **先问当前最阻断决策的点**：优先选「答了就能显著缩小方案空间」的问题；已由用户说清的维度跳过。
3. **答完再往下**：用户回答后，用 1 句复述/吸收关键信息，再问下一个问题；可简短说明还差哪一类信息，但不要预告一整串问题。
4. **可选答案要好答**：能用「是/否、二选一、具体事实」的就不要用宽泛开放题；必要时给 2–4 个选项供点选，仍只围绕这一题。
5. **何时出摘要**：仅当关键缺口已齐、或用户表示「够了/直接给方案」但仍须先对齐时，才输出「我目前的理解」并请确认；此前不要用大段待确认摘要打断对话。
6. **用户一次答了很多**：只吸收相关部分，从中挑出仍缺的**下一个**问题继续，不要因对方话多就改回批量追问。

## 阶段一输出结构

### 探询轮（缺口未齐时）

```markdown
（可选，1 句：刚吸收到的关键信息，或为何先问这个）

**问题：** …
（可选：A / B / C 等便于回答的选项）
```

不要在探询轮附带方案对比、推荐、或「下面还要问这些问题」的预告清单。

### 确认轮（关键缺口已齐、准备进入阶段二时）

```markdown
## 我目前的理解（待你确认）
- 目标：…
- 约束：…
- 主要利害域：…
- 利益方：…
- 已知缺口：无 / 仅剩 …（非阻断可标为假设）

请确认以上是否准确，或指出要改的地方；**确认后我再给出可选方案与利害对比。**
```

## 阶段二输出结构（确认后必须）

按此结构回复，可按场景删减小节，但**不得省略风险、坑点，以及对每条利害的成因解释**：

```markdown
## 决策背景
（1–3 句：已确认的目标、约束、利害所在）

## 可选方案
### 方案 A：…
- **适合**：…
- **收益**：…
- **代价 / 利害**：
  - …（利害是什么）—— **为何会出现**：…（一句话说清机制/因果）
- **坑点**：
  - 🔴 高：… —— **为何会出现**：…
  - 🟡 中：… —— **为何会出现**：…
  - 🟢 低：… —— **为何会出现**：…
- **如何处理**：若选此方案，按 … 执行；出现 … 时停止/回滚

### 方案 B：…
（同上）

## 对比摘要
| 方案 | 主要收益 | 主要风险 | 可逆性 | 建议对象 |
|------|----------|----------|--------|----------|
| A    | …        | …        | 高/中/低 | …      |

## 建议
- **默认推荐**：…（写清前提）
- **不建议**：…（写清原因）
- **需要你确认**：…（仅列真正阻断执行的问题；选定方案前不执行危险操作）
```

## 利害成因写法（必须，阶段二）

每条「代价 / 利害」和「坑点」都要解释**为什么会出现这个利害**，而不是只报结果。

- **写什么**：触发链条（做什么 → 系统/规则/他人如何反应 → 用户损失什么）
- **怎么写**：一句白话，非专业读者也能懂；点到机制即可，不堆术语
- **禁止**：只写「有风险」「可能损失」却不说因果；用黑话代替解释

**好：**「force push 改写已推送历史 —— **为何会出现**：别人已经基于旧提交拉过分支，你的新历史会和他们本地对不上，合并/推送会冲突或覆盖」

**差：**「force push 有风险，请谨慎」

## 风险级别约定

| 级别 | 含义 | 处理要求 |
|------|------|----------|
| 🔴 高 | 易造成重大或不可逆损害 | 必须写清触发条件、为何会出现、如何避免、失败时如何止损 |
| 🟡 中 | 有实质代价，但通常可缓解 | 写清为何会出现 + 检查项或缓解步骤 |
| 🟢 低 | 摩擦/体验问题为主 | 一句话成因即可 |

坑点要**具体可检验**（例如「未备份就迁移 → 数据不可恢复」），禁止空话（「注意安全」「谨慎操作」）。

## 行为准则

1. **先问后案**：未获用户对探询理解的确认前，不输出方案对比与推荐。
2. **一问一答**：阶段一每轮只问一个问题，像对话推进，不发问卷。
3. **多利益方视角**：提问覆盖决策者以外的受影响方与约束方，避免只站在「想快点做完」一侧。
4. **利害优先于便利**：不要为了推进任务而淡化风险。
5. **利害必带成因**：每条利害都说明「为何会出现」；用户应能复述因果，而不是只记住吓人结论。
6. **方案必须真实可选**：不要堆砌用户做不到的选项；缺权限/缺信息时标明。
7. **推荐带前提**：写「在 … 成立时选 A」；前提在阶段一未澄清就先问。
8. **区分事实与判断**：已知事实、假设、主观偏好分开写。
9. **危险操作降速**：方案确认后，执行破坏性命令或生产变更前，仍须用户明确选定方案。
10. **语言直接**：用中文，短句；避免恐吓式措辞，也避免过度安慰。
