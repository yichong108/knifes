# Catch 参考

`SKILL.md` 放流程与输出骨架；本文件补充发现透镜细则、严重度判定、示例与 skill 衔接。

## 发现透镜细则

### 症状 vs 根因

| 检查要点 | 示例 |
|----------|------|
| 用户抱怨的是现象还是原因 | 「慢」是症状；「未建索引导致全表扫」是根因 |
| 修症状是否会复发 | 只加缓存不修数据模型，根因仍在 |
| 是否有多层因果 | 延期 → 赶工 → 跳过 review → 线上故障 |

**好：**「问题：接口超时频发 —— **证据**：用户称高峰 5s+；方案只提加机器未提查询优化 —— **影响**：扩容无法消除慢查询根因」

**差：**「性能可能有问题」（无证据、无区分症状/根因）

### 假设与缺口

| 检查要点 | 示例 |
|----------|------|
| 方案依赖哪些未验证前提 | 「用户都会升级客户端」是否成立 |
| 关键数据是否缺失 | 无流量预估就做容量规划 |
| 成功标准是否定义 | 「上线顺利」无量化指标 |

缺证据的缺口写入「待确认」，不要写成已证实问题。

### 矛盾与不一致

| 检查要点 | 示例 |
|----------|------|
| 目标与手段是否一致 | 要「零停机」却计划直接改生产表结构 |
| 多处描述是否打架 | 文档写只读，代码有写接口 |
| 时间线与资源是否匹配 | 两周交付却列四个月功能 |

### 利益方盲区

| 检查要点 | 示例 |
|----------|------|
| 谁承担风险但未参与 | 运维未评审发布窗口 |
| 谁受益谁买单未说清 | 业务要功能，成本压给 infra |
| 外部方是否被忽略 | 客户合同里的 SLA 与内部计划不符 |

### 失败模式

| 检查要点 | 示例 |
|----------|------|
| 单点故障 | 只有一人会部署；只有一个 region |
| 无回滚路径 | 迁移脚本不可逆且无快照 |
| 异常路径未覆盖 | 第三方超时、部分失败、重复提交 |

### 依赖与约束

| 检查要点 | 示例 |
|----------|------|
| 隐藏依赖 | 依赖未文档化的内部服务、许可证、人力 |
| 资源不匹配 | 预算/人手/权限与承诺交付不符 |
| 外部约束 | 合规、合同、平台政策 |

## 严重度判定

| 级别 | 典型信号 | 反例（不要这样标） |
|------|----------|-------------------|
| 🔴 高 | 数据丢失、安全漏洞、不可逆生产变更、重大合规/资金风险 | 仅凭「感觉危险」无证据 |
| 🟡 中 | 可造成明显返工、延期、体验受损，通常有缓解手段 | 把一切不确定都标高 |
| 🟢 低 | 命名、文档、小摩擦、可维护性 | 把数据安全标成低 |

每条问题：**证据 → 影响 → 严重度** 三者一致；影响与级别不匹配时下调或上调并说明理由。

## 跨领域示例

### 示例 A — 技术上线方案

**检查对象**：用户描述的灰度上线方案（无回滚章节）。

**问题清单（节选）**：

- 🔴 **未定义回滚条件与步骤** —— 证据：方案只写「全量切换」，无失败判定与回退 —— 影响：异常时只能手工救火 —— 下一步：补充回滚触发条件、负责人、预计耗时
- 🟡 **监控指标未覆盖新业务路径** —— 证据：监控列表仍是旧接口 —— 影响：故障发现滞后 —— 下一步：列新路径 SLI 与告警阈值

### 示例 B — 团队协作流程

**检查对象**：用户描述的「需求直接进开发、无评审」现状。

- 🟡 **需求入口无统一评审** —— 证据：用户原话「产品文档口头同步」 —— 影响：范围漂移、返工 —— 下一步：定最小评审清单（目标、边界、验收）
- 🟢 **站会时长不固定** —— 证据：「有时 5 分钟有时 40 分钟」 —— 影响：时间不可预期 —— 下一步：限时 + 异步补材料

### 示例 C — 个人决策描述（catch 不替用户选）

**检查对象**：用户考虑跳槽的两段自述（薪资 vs 成长）。

- 🟡 **决策标准未排序** —— 证据：同时强调「钱最重要」和「必须学新技术」 —— 影响：选项对比时权重不清 —— 下一步：列出 3 条可排序的标准；若要做取舍可改用 choice
- **待确认**：现公司是否有未兑现承诺（用户未提供）

## 与 choice / concept 的衔接

| 用户意图 | 动作 |
|----------|------|
| 只要「有哪些问题」 | 本 skill 完整输出清单即可 |
| 「那选 A 还是 B / 要不要做」 | 清单交付后一句：涉及利害取舍可改用 **choice** |
| 「帮我讲透 XX 是什么」 | 一句：概念深入理解可改用 **concept**；catch 已标理解缺口则可停 |

**话术示例**：「以上是目前能证实的问题清单。若要在方案间取舍或评估是否继续，可以说一下，我们改用 choice 做利害对比。」

## 反模式

- 无证据堆问题清单
- 用「待确认」逃避：明明用户已给出事实仍标假设
- 问卷式连问多个澄清问题（违反最多 1 问）
- 在 catch 输出里写完整方案对比或默认推荐（应交给 choice）
- 展开概念四层讲解（应交给 concept）
- 严重度全是 🔴 或全是 🟢，无区分
