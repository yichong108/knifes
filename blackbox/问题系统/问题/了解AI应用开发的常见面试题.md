# 了解AI应用开发的常见面试题

1. LLM 应用里，Prompt、System Prompt、Context Window 分别解决什么问题？你怎么设计一层可维护的 Prompt？
2. RAG 的基本链路是什么？Chunk 切分策略、Embedding 选型、检索召回与重排序各自影响什么？
3. 什么时候该用 Agent / Tool Calling，什么时候用普通单轮问答就够了？如何控制 Agent 的循环与成本？
4. 如何评估一个 AI 应用的效果？你会设计哪些离线指标与在线指标，人工评测怎么落地？
5. Token、延迟、并发、成本怎么做预算与优化？流式输出（streaming）带来哪些工程取舍？
6. 如何处理幻觉、敏感内容与越权？你会做哪些护栏（guardrails）、过滤与审计？
7. 多轮对话的记忆怎么存？短期上下文、长期记忆、用户画像分别怎么设计，如何避免上下文污染？
8. 微调（Fine-tune）、LoRA、RAG、Prompt 工程各自适用什么场景？如何做技术选型？
9. 线上如何做可观测性：请求追踪、失败重试、模型降级、A/B 实验与回滚？
10. 如果要把大模型接到已有业务系统（鉴权、数据库、工作流），你会如何设计接口、权限与失败兜底？

## 第 1 题归档（2026-08-21）

### 三者分别解决什么


| 概念                 | 解决什么                                                      |
| ------------------ | --------------------------------------------------------- |
| **Prompt**         | 这一轮任务怎么说清楚：问题、约束、格式、示例                                    |
| **System Prompt**  | 应用级稳定设定：角色、边界、安全、输出契约、少量用户/租户画像                           |
| **Context Window** | 单次调用的 token 容量上限：System / User / 历史 / RAG / Tool 结果一共能塞多少 |


一句话：**System 定人格与规矩，User Prompt 定本次任务，Context Window 定能带多少行李。**

#### Context Window 易错点

- 不是「模型上下两端的文字」，而是一次推理能同时看见的 **token 容量**。
- 类比：工作台桌面大小，不是页眉页脚。
- 超窗 → 截断 / 摘要 / RAG，不是把 Prompt 再写长一点。
- 它不是长期记忆；窗口外的要另存，需要时再取回。



### 可维护 Prompt：分层 + 版本

1. **模板层**：结构稳定（角色、步骤、输出 schema）
2. **变量层**：用户名、订单号、检索片段等运行时注入
3. **策略层**：温度、模型、是否开工具——常和 Prompt 版本绑在一起做实验

版本建议：

- Prompt 自有版本：`prompt_id + semver`（如 `order_reply@2.3.1`）
- 应用绑定的是 **通道/标签**（如 `stable` / `canary`），不是把文案写死在代码里
- 回滚 = 改标签指向；不必回滚整个应用发版
- 在线改 Prompt 的「延迟」：配置拉取 + 短 TTL 缓存；长会话可钉死 `prompt_version`，避免中途人格突变
- 发布门禁：改文案 → 离线评测 → 小流量 A/B → 全量



### 解耦：什么解得开、什么解不开


| 层        | 能不能解耦 | 含义                                   |
| -------- | ----- | ------------------------------------ |
| **发版动作** | 能     | Prompt 文案改完不必跟着打应用包                  |
| **兼容契约** | 半耦合   | 占位符、输出 JSON、工具名须和应用代码对得上             |
| **产品效果** | 基本解不开 | 效果 = Prompt × 模型 × 检索/工具 × 业务逻辑 × UI |


要点：

- **同一 Prompt、不同应用**，效果可以完全不同——回滚 Prompt 只保证话术版本回去，不保证整体体验回去。
- 需要「回退到对应效果」时，钉的是 **experience / policy 组合**，例如：

```text
prompt + model + rag_index + tools_schema + app_compat
```

- 契约破坏性变更（输出格式、tool 变更）= major，应和应用同发。



### 要不要和应用解耦？（面试取舍）

取决于 **契约稳不稳** 和 **谁、多久改一次**：


| 场景                           | 倾向                            |
| ---------------------------- | ----------------------------- |
| Prompt 与解析/Tool 强绑定，几乎跟功能一起改 | Prompt 进仓库，跟应用同版本发——搭建成本低、易复现 |
| 产品/运营频繁单独调话术                 | Prompt 服务/配置 + 标签指版本；发布和应用解耦  |
| 要保效果 / 事故回滚                  | 用 policy 钉组合，不只回滚一段文案         |


结论一句：**发布可以解耦，效果与契约不能假装无关；不是一上来就上大平台。**

「耦合深就不必解耦、成本更低」——**早期或契约常变时成立**；等话术独立高频变更，再解耦发布。面试默认叙事用「按条件选型」，不要只押「必须解耦」或「永远不解耦」。

### 面试口述（约 40 秒）

> Prompt 和应用是不是解耦，取决于契约稳不稳和谁、多久改一次。  
> 若 Prompt 和解析逻辑、Tool 强绑定，且几乎跟功能一起改，我会把 Prompt 放仓库跟应用同版本发——搭建成本低，出问题也好复现。  
> 若产品要频繁单独调话术，再做成 Prompt 服务/配置，用标签指向版本，发布和应用解耦；但效果回滚要钉 Prompt+模型+检索等组合，不是只回滚一段文案。  
> 所以是发布可以解耦，效果与契约不能假装无关；不是一上来就上大平台。



### 本地模块怎么维护（不解耦发布时）

「本地模块」= Prompt 跟应用同仓、同发版；**不需要 Prompt 平台**，但也不能把长文案散落在业务函数里。

#### 目录与分层（和「可维护」同一套）

```text
prompts/
  order_reply/
    system.md          # 稳定角色/边界
    user.jinja         # 本次任务模板（占位符）
    schema.ts          # 期望输出契约（Zod 等）
    meta.yaml          # prompt_id、semver、默认 model/温度
```

- **模板层**进文件；**变量层**在代码里 `render(template, vars)`；**策略层**（model/温度）写在 `meta` 或配置，跟该 Prompt 版本一起改。
- 业务代码只 `loadPrompt('order_reply')`，不内联几千字字符串。



#### 版本靠 Git，不靠独立服务


| 做法                            | 作用                       |
| ----------------------------- | ------------------------ |
| 文件旁 `meta.version`（如 `2.3.1`） | 日志/评测可钉死「用的是哪版文案」        |
| PR 改 Prompt                   | 和改代码一样 review；产品可参与 diff |
| Commit / tag                  | 回滚 = 回退该文件或整个应用发版        |
| 请求日志打 `prompt_id@version`     | 线上问题可复现到具体文案             |


可选轻量开关：仓库里保留 `v2`/`v3` 两套文件，用环境变量或 feature flag 选加载哪套——**仍是本地模块**，只是发版粒度比「整包回滚」细一点。

#### 门禁（本地也能做）

1. **渲染测试**：占位符必填、缺变量直接失败（防空上下文上线）。
2. **契约测试**：模型输出（或 mock）过 schema；破坏性改输出格式 = major，和应用解析同 PR。
3. **离线小评测集**：改 Prompt 跑一轮 golden / LLM-as-judge；挂在 CI，不过不合并。
4. **变更说明**：PR 写清改了角色/步骤/格式哪一块，方便事故追溯。



#### 和「Prompt 服务」差在哪


|     | 本地模块                             | Prompt 服务/配置中心 |
| --- | -------------------------------- | -------------- |
| 发布  | 跟应用发版（或 flag 切本地多版本）             | 改标签即可，不必打应用包   |
| 复现  | Git commit + `prompt_version` 足够 | 还要查配置中心历史      |
| 成本  | 低，早期默认                           | 话术高频独立变更时再上    |


一句话：**本地维护 = 独立目录 + 模板/变量/契约分文件 + Git 当版本源 + CI 评测；发布可以暂时和应用绑死，可维护性靠结构，不靠平台。**

#### 面试口述（本地模块，约 30 秒）

> 如果只做本地模块，我会把 Prompt 从业务代码里抽到 `prompts/`：system、user 模板、输出 schema、版本元数据分开。  
> 版本用 Git 和文件里的 semver，请求日志带上 `prompt_id@version`；改文案走 PR，挂渲染测试和一小撮离线评测。  
> 需要细一点回滚时，仓库里留多版本文件加 flag 切换，不必一上来上 Prompt 平台。



### Skills / Tools 里的 Prompt 怎么维护

业务话术可以考虑配置中心；**Skill / Tool 的文案几乎默认跟代码同仓**——它们不是「对用户怎么说」，而是「教模型何时调用、怎么填参、按什么流程做事」，和实现是同一份契约。

#### 两类文案分别是什么


| 类型               | 典型载体                                       | 模型拿它做什么         |
| ---------------- | ------------------------------------------ | --------------- |
| **Tool Prompt**  | `name` / `description` / 参数说明（JSON Schema） | 选不选这个工具、参数怎么填   |
| **Skill Prompt** | `SKILL.md`（何时启用、workflow、禁止项）              | 多步流程、边界、何时读参考文档 |


二者都占 Context Window；写太长会挤掉对话与 RAG。

#### 为什么不宜做成「可热更话术」

- 改 Tool 描述却不改实现 → 模型乱调、参数对不上。
- 改实现却不改描述 → 模型不知道新能力，或仍按旧约束调用。
- Skill 的 workflow 常直接对应代码步骤 / 门禁；和业务「改个语气」不是一类变更。

结论：**Skill/Tool Prompt = 接口文档的一部分，跟 tool 实现、skill 脚本同 PR、同版本发。**

#### 本地怎么维护（推荐默认）

```text
tools/
  search_orders/
    schema.ts       # name、description、parameters（唯一真源）
    handler.ts      # 实现
    evals.yaml      # 该选此 tool 的用例 / 不该选的用例
skills/
  refund_flow/
    SKILL.md        # 启用条件、步骤、禁止项
    references/     # 长说明外置，按需再读，避免常驻占窗
```

要点：

1. **描述与实现同目录、同 PR**；破坏性改参名/语义 = major，调用方与评测一起改。
2. **Tool 描述写短、写准**：做什么、何时用、何时不用、副作用；少塞业务散文。长流程放 Skill，不堆进每个 tool 的 description。
3. **Skill 分层加载**：目录里先给短 description 做路由；真正启用再注入全文 / 再读 `references/`，省窗口。
4. **版本**：Git +（可选）skill/tool 的 `metadata.version`；日志记下本轮挂载的 `tools_hash` / `skill_ids@version`，和业务 `prompt_version` 一样可复现。
5. **评测门禁**：
  - Tool 选择：给定用户话，是否点到正确工具、是否误点；
  - 填参：关键字段是否正确；
  - Skill：是否在该启用时启用、是否遵守禁止项（可用固定剧本跑 Agent）。



#### 和业务 Prompt 的分工


|         | 业务 System/User Prompt | Skill / Tool Prompt |
| ------- | --------------------- | ------------------- |
| 改动频率与动机 | 话术、风格、产品实验            | 能力边界、流程、API 契约      |
| 发布解耦    | 契约稳且高频时可配置化           | 默认不解耦，跟代码走          |
| 优化目标    | 回答质量、格式               | 选对工具、少乱调、流程可重复      |


一句话：**业务 Prompt 管「怎么答」；Tool/Skill Prompt 管「能调什么、按什么剧本调」——后者当代码契约维护，用同仓 + 选择/填参评测，而不是当运营文案热更新。**

#### 澄清：「跟代码走」≠「混杂在代码里」

**「糊在业务函数里」**指的是：给模型看的长段文字，直接写进「处理订单 / 调 API」这种业务代码的字符串里，和 if/else、数据库调用揉在同一段函数中。

##### 反例（糊在一起）

```ts
async function handleUserMessage(msg: string) {
  // 下面整段是给模型的说明，却塞在业务函数中间
  const systemPrompt = `
你是客服助手。退款时必须先查订单，再……（此处几十上百行）
可用工具 search_orders：当用户提到订单号时调用……
参数 orderId 必须是……
禁止在未确认时直接退款……
`;
  const order = await db.findOrder(...);  // 真业务
  return await llm.chat({ system: systemPrompt, user: msg });
}
```

问题：改一句提示词要翻业务代码；无法单独 review 文案；也难给 Prompt 打版本、做评测。

##### 正例（分文件邻接，仍跟代码同仓）

```text
tools/search_orders/schema.ts   ← 短 description（给模型选工具）
tools/search_orders/handler.ts  ← 只负责查库
skills/refund_flow/SKILL.md     ← 长流程说明
prompts/cs_agent/system.md      ← 角色与边界
```

```ts
async function handleUserMessage(msg: string) {
  const system = loadPrompt('cs_agent/system');
  const tools = loadToolSchemas(['search_orders']);
  // 需要时再 loadSkill('refund_flow')
  return await llm.chat({ system, tools, user: msg });
}
```


| 说法          | 一句话                                         |
| ----------- | ------------------------------------------- |
| **糊在业务函数里** | 长 Prompt 和查库/发请求写在同一个函数字符串里                 |
| **跟代码走**    | Prompt 仍在仓库里，但是**单独文件**，和 `handler` 并排，一起发版 |


所以那句「不是把长 Prompt 糊在业务函数里」= **别把说明书抄进干活的函数里**；说明书单独放，干活的函数只负责加载和执行。

#### 面试口述（Skill/Tool，约 25 秒）

> Skills 和 Tools 里的 description、SKILL 正文也是 Prompt，但和业务话术不同：它们和实现强绑定，我会默认放仓库，跟 handler 同 PR。  
> Tool 描述保持短而准，长流程进 Skill，并做分层加载省 context；日志带上挂载的 skill/tool 版本。  
> 门禁重点是工具选择和填参评测，而不是把这类文案丢到配置中心热更。  
> 跟代码走是同版本发；长说明放 schema / SKILL.md，业务函数只 load，不把说明书抄进函数中间。

## 第 4 题归档（2026-08-22）

### 总原则：先定「好」是什么，再选指标

AI 应用的「效果」不是单一分数，而是三层：


| 层 | 问的是什么 | 典型信号 |
| --- | --- | --- |
| **任务正确** | 该做的事做对了没有 | 事实对、工具选对、格式合规 |
| **体验可用** | 人愿不愿意继续用 | 有帮助、清晰、少废话、延迟可接受 |
| **业务成功** | 是否推动业务目标 | 转化、工单关闭、留存、客服人工接管率 |


一句话：**离线保证不崩、不退步；在线证明对业务有用；人工校准「分数」和「真好」对得上。**

发布默认链路：

```text
改 Prompt/模型/检索 → 离线门禁 → 小流量 A/B → 人工抽检 → 全量
```



### 离线指标（发布前、可复现、适合 CI）

先建 **评测集（eval set）**：golden cases + 难例 + 安全用例；每条钉死 `input`、可选 `expected`、标签（场景/难度/是否需工具）。

#### 1. 任务层（有标准答案时优先）


| 指标 | 适用 | 怎么算 |
| --- | --- | --- |
| **Exact / 字段准确率** | 结构化输出、填表、抽槽 | 关键字段对不对 |
| **工具选择正确率** | Agent / Tool Calling | 该调的调了、不该调的没调 |
| **填参正确率** | Tool | `orderId` 等关键参是否正确 |
| **检索召回@K / MRR** | RAG | 相关 chunk 是否进 Top-K |
| **引用忠实度** | RAG 问答 | 答案是否被检索片段支持（可规则或 LLM-judge） |
| **幻觉率（代理）** | 开放问答 | 相对 golden / 知识库的冲突比例 |


#### 2. 质量层（开放生成）


| 指标 | 说明 | 注意 |
| --- | --- | --- |
| **LLM-as-Judge** | 用强模型按 rubric 打分（正确性/完整/语气/安全） | 要校准；固定 judge 模型与 prompt 版本 |
| **Pairwise win-rate** | A vs B，哪边更好 | 比绝对分更稳，适合改版对比 |
| **Rubric 分项分** | 拆成可行动维度，不只给总分 | 方便定位是「事实错」还是「废话多」 |


传统 BLEU/ROUGE 对对话/客服类通常弱相关，**不当主指标**；有严格参考答案的摘要/翻译可作辅。

#### 3. 工程与安全门禁（也算离线）


| 指标 | 为什么算效果 |
| --- | --- |
| **Schema 通过率** | 输出解析失败 = 功能失败 |
| **延迟 P50/P95（回放）** | 太慢也是差体验 |
| **成本 / 请求 token** | 同样质量下更贵 = 不可持续 |
| **拒答/越权用例通过率** | 安全回归；不过不合并 |


#### 离线落地要点

1. **集要小而难**：先 50–200 条高质量，覆盖主路径 + 边界 + 红线；别堆几千条噪声。
2. **版本钉死**：`prompt@version` + `model` + `rag_index` + `judge@version`，否则分数不可比。
3. **挂 CI**：改 Prompt/检索策略，离线套跑不过不合并（或仅 warning + 人工签核）。
4. **分层跑**：契约/工具选择（快、确定性）每 PR；LLM-judge（慢、贵）合入前或 nightly。



### 在线指标（真实流量、证明业务价值）

分三类，面试时按「体验 → 任务 → 业务」说。

#### 1. 体验与互动


| 指标 | 含义 |
| --- | --- |
| **点赞/点踩率**、显式评分 | 直接反馈，样本少但准 |
| **再问率 / 追问轮次** | 过高可能没一次说清；过低也可能敷衍结束——要结合场景解读 |
| **会话完成率**、中途放弃率 | 是否走完预期流程 |
| **复制/采纳率**（代码助手等） | 用户是否真用了输出 |
| **首 token 延迟、整段延迟、流式卡顿** | 体验硬指标 |


#### 2. 任务成功（尽量可自动打标）


| 场景 | 在线任务指标示例 |
| --- | --- |
| 客服 | 一次解决率、转人工率、工单关闭时长 |
| RAG 知识问答 | 有用点击、后续是否搜文档/找人 |
| Agent | 工具成功率、无意义重试次数、任务完成标记 |
| 搜索/推荐式 AI | CTR、下游转化 |


#### 3. 业务与成本护栏


| 指标 | 作用 |
| --- | --- |
| **北极星**（转化、CSAT、人工成本下降等） | 最终裁决改版值不值得 |
| **$/成功会话、token/会话** | 质量涨但成本炸也要拦 |
| **错误率、超时率、降级触发率** | 稳定性也是效果的一部分 |
| **安全：拦截率、误杀率、上报工单** | 护栏是否过紧/过松 |


#### 在线实验怎么做

- **A/B**：同一流量随机分到 policy 组合（prompt+model+rag…），看在线指标 + 离线回归。
- **护栏指标**：主指标升但转人工暴涨 / 安全事件增多 → 自动停实验。
- **日志可复现**：每条请求带 `experience_id`（policy 指纹），坏 case 能拉回离线集。



### 人工评测怎么落地

人工不是「偶尔看看」，而是 **校准器 + 难例矿工**。

#### 1. 评什么：固定 Rubric


| 维度（示例） | 1–5 或 通过/失败 |
| --- | --- |
| 事实正确 / 是否幻觉 | 必评 |
| 是否完成用户意图 | 必评 |
| 是否简洁、可执行 | 按产品 |
| 语气/品牌合规 | 按产品 |
| 安全与越权 | 一票否决 |


尽量 **分项 + 总体**；只给「好/不好」难指导改 Prompt。

#### 2. 评哪些样本


| 来源 | 用途 |
| --- | --- |
| 离线 golden 抽样 | 校准 LLM-judge、回归基线 |
| 在线点踩 / 转人工 / 长会话 | 挖真实失败模式 |
| 主动对抗集（越权、诱导幻觉） | 安全门禁 |


#### 3. 谁评、怎么控质量

1. **双人盲评 + 抽检**：关键变更至少两人；算 **一致率 / Cohen’s κ**，分歧仲裁。
2. **对照评**：同一题看 A/B 输出（顺序随机），比绝对打分稳。
3. **专家 vs 众包**：事实/合规用懂业务的人；语气可扩大范围，但要培训 + 样例标定。
4. **节奏**：日常——每周抽 N 条在线坏例入库；发版——改动相关切片全量人工或加严抽检。

#### 4. 和自动评测闭环

```text
人工标出坏 case → 写入 eval set → 离线回归防再犯
         ↓
   用人工分校准 LLM-judge（相关/偏差）
         ↓
   judge 可放心进 CI；人工转向难例与新场景
```

人工贵，所以目标是：**缩小必须人评的比例，而不是取消人评。**



### 按应用类型快速选型（面试加分）


| 类型 | 离线主指标 | 在线主指标 | 人工重点 |
| --- | --- | --- | --- |
| RAG 问答 | 召回@K、引用忠实、答案正确 | 有用率、追问、转人工 | 幻觉与漏引 |
| Agent | 工具选择/填参、轨迹成功 | 任务完成、重试、成本 | 该不该调工具、副作用 |
| 开放聊天/陪伴 | rubric / pairwise | 留存、会话时长、举报 | 安全与体验边界 |
| 结构化助手 | 字段准确、schema | 采纳率、返工率 | 业务规则对错 |



### 面试口述（约 45 秒）

> 评估分三层：任务做对没有、体验能不能用、业务有没有变好。  
> 离线用评测集做门禁：有标准的看字段/工具选择/RAG 召回与忠实度；开放生成用 rubric 或 pairwise，必要时 LLM-as-judge，并配 schema、安全用例和延迟成本；版本钉死才能进 CI。  
> 在线看点赞点踩、完成率、转人工、任务成功，再挂北极星和 $/会话；改版走 A/B，护栏指标恶化就停。  
> 人工用固定分项 rubric，抽 golden + 点踩/转人工坏例，双人盲评算一致率，标完的 case 回写离线集，并用来校准 judge——人负责校准和挖难例，不是替代全部自动评测。

## 第 3 题归档（2026-08-22）

### 什么时候用单轮 / Tool Calling / Agent

判据：**步骤是否事先可枚举、要不要根据中间结果改计划。** 不是「凡调工具就上完整 Agent」。


| 场景 | 选型 |
| --- | --- |
| 生成标题、改写、分类、单次总结——一次出结果 | **单轮问答** |
| 固定「先查再答」、步数可知 | **单轮 + 一次（或少量）Tool Calling** 往往够 |
| 步数未知、要观察 tool 结果再决策、多分支 | **Agent（ReAct 式循环）** |


用户初版口误纠正：需要本地/外部工具且多步时才倾向 Agent；纯生成不必上 Agent。

一句话：**单轮管「一次说清」；Tool Call 管「固定动作」；Agent 管「边做边看」。**



### 如何控制循环与成本

四道闸，面试按这个说：

1. **最大步数**：硬顶可到几十（如 50）；产品侧常见 8–20，大任务再放宽  
2. **预算墙**：单次请求上限（token / 金额 / 墙钟时间），触顶停并返回「做到哪了」  
3. **上下文**：不只限 `max_output`；历史与 tool 结果要摘要/裁剪，否则越跑越贵  
4. **停止条件**：任务完成、模型不再调工具、用户中断——任一触发即结束



### 出错了怎么办

不追求从不失败，而要 **失败可预期、可停止、可交代**：

1. **工具失败**：错误回灌给模型换路；同 tool + 同参连败 N 次 → 强制停  
2. **死循环检测**：短窗口重复无效步骤 → 打断  
3. **降级**：Agent 失败 → 退回单轮/无工具，或返回部分结果 + 卡点  
4. **高风险操作**：写库/发消息/扣款前确认或人工闸门  
5. **可观测**：每步记 tool、耗时、token，便于复盘  

口述补一句：**成本靠步数/预算/上下文三道闸；出错靠回灌重试、死循环熔断、降级与审计。**



### 对照：pi-agent 有没有对应参数

`@earendil-works/pi-agent-core` **不全有开箱参数**——偏循环骨架 + 钩子，不像 Claude Agent SDK 直接给 `maxTurns` / `maxBudgetUsd`。


| 面试点 | pi-agent-core | coding-agent / 扩展 |
| --- | --- | --- |
| 最大循环 | 无内置 `maxTurns`；用 `shouldStopAfterTurn` 自计 | 编排层 `pi-agents` 才有 `maxTurns` / `maxIterations` 等 |
| 成本上限 | 无内置 `maxCost` | `/session` 可看花费；硬顶靠扩展（如 `pi-agent-budget`）或钩子自算 |
| 上下文 | `transformContext` | `compaction.*`（reserve / keepRecent） |
| 工具闸门 | `beforeToolCall` / `afterToolCall` / `terminate` | `defaultTools`、`--tools` / `--exclude-tools` |
| 出错 | 工具 `throw` → `isError` 回灌；`continue()` / `abort()` | `retry.enabled` / `maxRetries`（偏瞬时错误） |


心智：循环默认跑到模型不再调工具或你钩子/`abort` 停掉；**步数墙、钱墙要自己接**。



### 延伸：为何 DeepSeek Harness 不直接用 pi（与 NIH）

- **不是 pi 不好**，是角色不同：pi = 最小可嵌入 harness；DeepSeek Harness = 自家产品/实验平台（Everything is a Plugin，loop 也可替换），要与模型共进化、占生态叙事。  
- 模型厂把 harness 当产品一半时，**核心循环外包 = 控制权外包**；架构上「loop 也是插件」与 pi「核心已有一套 loop」也不天然贴合。  
- **NIH（Not Invented Here，非我发明）**：贬义指「外面已有仍无充分理由排斥」；有许可/安全/共进化/产品差异化等可说清的理由时，叫**正当自研**，不要乱贴 NIH。  
- 对个人/小团队：大厂自研逻辑往往不成立，优先复用；对卖模型+agent 的平台：自研壳常是战略默认项。



### 延伸：DeepSeek Harness 骨架 vs 工程实践缺口

当前重心大致是 **Cordis（插件总线）+ 基础应用壳**（loop 可替换、工具接入、会话跑通）——交付的是**可扩展骨架**，不是生产级 harness 工程全集。读 repo 常有「架构很完整、工程很薄」感。

| 层 | 常见缺口（多半要自建/插件补） |
| --- | --- |
| 控制面 | 步数墙、预算墙、死循环熔断、降级路径 |
| 上下文 | compaction / 摘要、tool 结果裁剪、会话预算 |
| 工具面 | 权限分级、沙箱、危险操作确认、同参连败熔断 |
| 可观测 | 逐步 trace、token/耗时分账、失败归因 |
| 产品运维 | Prompt/策略版本、回滚、A/B、多模型路由 |
| 评测 | 离线 case、线上护栏、与 harness 事件对齐 |

一句话：**Cordis + 基础 app = 怎么「长」能力；生产 harness 工程 = 怎么「管住、看清、可回退」。** DeepSeek 现阶段主攻前者；后者与 pi 类似，多在钩子/插件层自接。



### 面试口述（约 40 秒）

> 单轮管一次生成；固定「先查再答」用 Tool Calling 就够；步数未知、要边看边决策才上 Agent。  
> 循环用最大步数、token/金额/耗时预算、上下文裁剪和明确停止条件卡住；出错把工具错误回灌，同参连败和死循环要熔断，失败就降级并打日志。  
> 框架若像 pi 只给钩子没有 maxTurns/maxCost，生产上要在 `shouldStopAfterTurn` 一类边界自己接预算——循环骨架能复用，成本墙通常要自研一层。  
> DeepSeek Harness 亦然：Cordis 解决扩展权，生产控制面/可观测/评测多半仍要自建。

## 第 5 题归档（2026-08-22）

### 总原则：四维一起预算，别只盯单价

Token、延迟、并发、成本是同一笔账的四个面：


| 维 | 预算问什么 | 优化主杠杆 |
| --- | --- | --- |
| **Token** | 单次/会话能吃多少上下文与输出 | 裁剪、摘要、分层加载、缓存、小模型分流 |
| **延迟** | 用户可接受的首 token / 整段时间 | 流式、并行检索、路由到更快模型、预热 |
| **并发** | 峰值 QPS 与排队上限 | 限流、队列、多 key/多供应商、降级 |
| **成本** | $/成功会话、月度上限 | 以上全部 + 缓存命中 + Agent 步数墙 |


一句话：**先定 SLA（延迟 + 成功率）和预算墙（$/会话、token/会话），再倒推模型路由、上下文策略和限流；优化从「少送、少生成、少循环」下手，而不是先换更贵的模型。**

发布默认链路：

```text
算基线（token/延迟/$）→ 设预算墙与告警 → 裁剪与缓存 → 路由/降级 → 压测并发 → 上线盯护栏
```



### Token：怎么预算与优化

#### 1. 先分账，再设上限

一次调用大致：

```text
System + Skill/Tool 描述 + 历史 + RAG/检索 + 用户本轮 + 预留输出
```

| 做法 | 作用 |
| --- | --- |
| **分桶配额** | 如历史 ≤40%、RAG ≤30%、系统/工具 ≤15%、输出预留 ≥15%（按产品调） |
| **会话预算** | 不只 `max_tokens`；多轮累计 token / 金额触顶则摘要或开新会话 |
| **Agent 再加一道** | 每步 tool 结果也占窗；总步数 × 平均上下文 ≈ 真实 token 爆炸点 |


#### 2. 优化杠杆（按性价比）

1. **少送**：历史滑动窗口 + 摘要；RAG Top-K 与 chunk 长度收紧；Tool/Skill 分层加载（见第 1 题）。
2. **少生成**：约束输出 schema、禁止废话；`max_output` 按任务设，别默认拉满。
3. **能缓存就缓存**：稳定 System / 工具 schema 走 **Prompt Cache**（若供应商支持）；相同检索结果短 TTL 缓存。
4. **能短路就短路**：分类/抽槽用小模型或规则；只有难例进大模型。
5. **语义缓存（慎用）**：相似问命中历史答案；要标「可能过期」，写操作/强时效场景慎开。



### 延迟：怎么预算与优化

拆开量，面试别只说「加快」：


| 指标 | 含义 | 产品含义 |
| --- | --- | --- |
| **TTFT（首 token）** | 点发送到第一个字 | 体感「有没有在听」 |
| **TPOT / 生成速率** | token/s | 读起来顺不顺 |
| **E2E** | 到完整可用答案 | 能否点「采纳/提交」 |
| **P95/P99** | 尾延迟 | 高峰是否崩体验 |


常见构成：`网关排队 + 检索/工具 + 模型排队 + 预填(prefill) + 解码(decode)`。

#### 优化顺序（工程上常这样砍）

1. **流式**：先把 TTFT 体感做出来（见下文取舍）。
2. **并行**：检索与必要准备并行；多工具能并行就别串行。
3. **路由**：简单请求 → 小/快模型；复杂再升级（或投机：快模型先出，校验失败再重跑）。
4. **上下文减肥**：更短 prompt → 更短 prefill → 往往更快也更便宜。
5. **连接与复用**：keep-alive、区域就近、避免每次冷启动整条链。
6. **超时与降级**：P95 超预算 → 截断生成 / 换快模型 / 返回检索摘要 + 「完整版生成中」。



### 并发：怎么预算与优化

LLM 瓶颈常在 **供应商 RPM/TPM** 和 **自建推理的 KV/算力**，不是你应用服务器 CPU。

| 层 | 做法 |
| --- | --- |
| **准入** | 用户/租户级 QPS、并发会话上限；超限排队或友好拒绝 |
| **出站** | 对模型 API 做令牌桶（按 RPM + TPM 双限）；多 key / 多供应商 failover |
| **队列** | 异步任务（长报告、批量）进队列；在线对话走低延迟通道，避免互相抢 |
| **背压** | 上游快、模型慢时：限制 in-flight；Agent 步数高时按「会话」占槽而非按「HTTP」 |
| **降级剧本** | 429/超时 → 重试（抖动退避）→ 换模型 → 只读缓存/模板答 → 转人工 |


压测要按 **真实上下文长度** 打，空 prompt 的 QPS 没有参考价值。



### 成本：怎么预算与优化

#### 1. 成本公式（心里要有数）

```text
$/会话 ≈ Σ (input_tokens × p_in + output_tokens × p_out) × 调用次数
         + 检索/工具/托管费
```

Agent：调用次数 ≈ 循环轮次；tool 结果回灌会抬高后续 input。

#### 2. 预算怎么定

| 做法 | 说明 |
| --- | --- |
| **按成功会话** | 北极星用 `$/成功任务`，不是只看 `$/千 token` |
| **分场景单价** | 客服一通、代码补全一次、批量摘要一批，分别设墙 |
| **告警与硬顶** | 日/月预算；单用户异常刷量熔断 |
| **和效果一起看** | 成本降但转人工暴涨 = 假节省（呼应第 4 题护栏） |


#### 3. 优化清单（面试可按「减量 → 换路 → 谈判」说）

1. 减 input/output（裁剪、摘要、schema、短答）。
2. 减调用次数（合并步骤、能单轮+tool 就不上长 Agent；见第 3 题）。
3. 模型分层路由 + 缓存。
4. 批处理走便宜模型/异步；高峰只保在线路径。
5. 合同与用量：预留包、缓存折扣、批量 API。



### 流式输出（streaming）：工程取舍

#### 带来什么

| 收益 | 代价 / 复杂度 |
| --- | --- |
| **TTFT 体感好**，用户更不容易以为卡死 | 连接更长（SSE/WebSocket），网关超时、负载均衡要按长连接配 |
| 可 **提前取消**（用户点停），省尾部 decode 成本 | 取消要传到模型侧；半截 UI/业务状态要能收尾 |
| 可边生成边渲染、边解析 | **不完整 JSON**、Markdown 半截、XSS/注入要按增量处理 |
| 便于打字机动效与进度感 | 重试/断线续传难；「同一条回复」的幂等与日志要按 stream id 设计 |


#### 关键工程坑（面试加分）

1. **结构化输出**：流式时别假设整段 JSON 一次到位——用增量解析，或流式只出自然语言，最终再一枪非流式刷 schema；或约束为 line-delimited JSON。
2. **安全与护栏**：敏感词/越权若只在结束后审，危险字可能已经上屏——要 **增量审** 或延迟展示高风险片段；拦截后如何撤回已推 token 要有产品策略。
3. **计费与计量**：按最终 usage；中断要记实际生成量；别在首包就算「成功会话」。
4. **错误模型**：中途 429/断流 → 明确「可续写 / 需重来」；UI 区分「还在生成」和「已失败」。
5. **缓存与 CDN**：流式响应通常 **不可常规定长缓存**；语义缓存命中时可直接非流式或假流式吐缓存。
6. **观测**：除 E2E 外必盯 TTFT、token/s、断流率、取消率。


#### 何时可以不流式

- 只要最终 JSON/工具参数、且很短。
- 必须原子成功（签名、扣款指令）——先完整生成并校验再展示。
- 批处理、离线评测、CI。

一句话：**对流式买的是体感与可取消；付出的是长连接、增量解析、增量安全与半截状态机。**



### 四维怎么一起做（一张作战图）

```text
请求进入
  → 租户限流 / 预算墙（并发 + $）
  → 路由：规则/小模型 or 大模型
  → 组上下文（分桶裁剪 + cache）
  → 调用（流式 / 非流式）
  → 增量护栏 + 用量累计
  → 触顶：摘要 / 停 Agent / 降级 / 拒绝
```

| 目标 | 优先动哪几项 |
| --- | --- |
| 体感慢 | 流式 + 减 prefill + 快模型路由 |
| 账单炸 | 减 output、减 Agent 步数、缓存、小模型分流 |
| 高峰 429 | TPM 限流、队列分层、多供应商、降级剧本 |
| 质量不够 | 别只加长上下文；先评测（第 4 题）再决定是否加 RAG/换模 |



### 面试口述（约 45 秒）

> Token、延迟、并发、成本要一起预算：先定首 token/整段 SLA 和 $/成功会话，再给上下文分桶、给会话和 Agent 加 token/金额墙。  
> 优化先少送少生成少循环，再叠加 Prompt Cache、小模型分流和检索并行；并发按供应商 RPM/TPM 做令牌桶和降级，压测必须带真实上下文长度。  
> 流式换来更好的 TTFT 和可取消，但要处理长连接、半截 JSON、增量安全和断流续写；只要原子结构化结果或批处理，可以不流式。  
> 成本下降若换来转人工或失败率上升，不算省——和效果护栏一起看。

## 第 6 题归档（2026-08-22）

### 总原则：三类风险，三层防线

| 风险 | 本质 | 不能只靠什么 |
| --- | --- | --- |
| **幻觉** | 模型把「听起来对」当成「有依据」 | 只加一句「不要编造」 |
| **敏感内容** | 输入/输出触碰政策、法务、品牌红线 | 只靠模型自觉拒答 |
| **越权** | 用自然语言绕过鉴权，读/写不该碰的数据与动作 | 只靠 Prompt 写「别越权」 |

一句话：**Prompt 定规矩；代码与权限定硬边界；审计把违约变成可发现、可复盘。**

默认链路：

```text
入站鉴权 → 输入过滤/脱敏 → 组上下文（仅授权数据）→ 模型
  → 输出护栏（事实/敏感/schema）→ 工具执行前二次鉴权 → 审计日志
```



### 幻觉：怎么压、怎么验

幻觉消不完，目标是 **可证明、可拒答、可降级**。

#### 1. 产品与架构层（比调 Prompt 更管用）

| 手段 | 作用 |
| --- | --- |
| **RAG + 强制引用** | 答案必须能指回检索片段；无命中则拒答或只给「未找到」 |
| **结构化 / 工具查真相** | 订单状态、库存、价格走 API，不让模型「猜库」 |
| **不确定就降级** | 低置信 / 无依据 → 澄清问题、转人工、返回检索摘要而非编结论 |
| **缩小生成自由度** | 填表、分类、抽槽优先；开放散文只在允许场景开 |

#### 2. 生成时约束

1. System：无依据不编、区分「知识库说了」和「模型推断」。
2. 输出契约：`answer` + `citations[]` / `confidence`；无 citation 时 UI 不展示成「确定事实」。
3. 温度偏低；关键字段用 schema 校验，过不了就重试或拒答。

#### 3. 生成后校验（护栏）

| 校验 | 做法 |
| --- | --- |
| **引用忠实度** | 答案关键主张是否被 chunk/工具结果支持（规则 + LLM-judge） |
| **与工具结果一致性** | 模型叙述 vs API 返回字段 diff |
| **自洽 / 二次核对** | 高风险答复另跑一轮「是否有依据」审核模型（贵，只打关键路径） |

离线：幻觉对抗集进评测（第 4 题）；在线：点踩、纠错、转人工回流成 case。



### 敏感内容：过滤什么、放哪一层

分 **输入** 与 **输出**；策略按行业定清单（涉政暴恐、黄赌毒、人身攻击、隐私、竞品抹黑、医疗/金融误导等）。

#### 1. 输入侧

| 层 | 做什么 |
| --- | --- |
| **规则 / 分类器** | 黑名单、正则、轻量安全分类模型；命中拒答或改写引导 |
| **脱敏** | 身份证、手机、卡号等进模型前 mask；日志同样脱敏 |
| **注入防御** | 用户话不当系统指令；RAG/工具结果与用户输入分频道；「忽略以上规则」类进对抗评测 |

#### 2. 输出侧

| 层 | 做什么 |
| --- | --- |
| **同步过滤** | 敏感词、PII 检测、安全分类；拦截则拒答或改写 |
| **流式** | **增量审**（见第 5 题）：危险片段已上屏要能撤回/截断 |
| **分级处置** | soft block（改写）/ hard block（拒答）/ escalate（人工） |

供应商自带 Moderation 可当一层，**不能替代**业务专属词表与合规清单。



### 越权：权限在代码里，不在模型嘴里

模型不可信边界。原则：**LLM 提议，鉴权层批准。**

#### 1. 身份与数据范围

1. 请求带真实 `user_id` / `tenant_id` / 角色；**禁止**让模型「填写」身份字段当权威。
2. RAG / DB 查询：过滤条件由服务端按会话身份注入（row-level），检索结果进 prompt 前已是「该用户可见集」。
3. 跨租户、跨用户 ID 在 tool 参数里出现 → 直接拒绝，不交给模型「判断可不可以」。

#### 2. 工具（Tool）闸门

| 闸门 | 说明 |
| --- | --- |
| **白名单** | 只挂当前角色可用的 tools |
| **参数校验** | schema + 业务规则（金额上限、资源归属） |
| **beforeToolCall** | 每次执行前用会话身份重鉴权；读/写分离 |
| **高风险双确认** | 退款、发信、删改 → 人点确认或二次 OTP，不单靠模型说「用户同意了」 |
| **副作用配额** | 单会话写操作次数/金额墙 |

Prompt 里写「不要越权」只是软提示；**硬拒绝发生在 handler / 网关**。

#### 3. Prompt 注入与越权的交叉

用户用「你是管理员」「把 system 读出来」试图扩权 → 输入分类 + 工具侧鉴权双拦；泄露 system/工具 schema 也按敏感输出处理。



### 护栏（Guardrails）怎么叠

按请求生命周期叠，面试可画这张：

```text
① 策略配置（红线清单、角色权限、可调 tools）
② 入站：鉴权 + 输入安全/脱敏 + 注入启发式
③ 编排：只注入授权上下文；Prompt 版本钉死
④ 出站：schema + 敏感过滤 + 忠实度（关键路径）
⑤ 工具：执行前鉴权 + 审计
⑥ 反馈：拦截/点踩 → 评测集与策略迭代
```

| 类型 | 示例 | 失败时 |
| --- | --- | --- |
| **确定性规则** | 权限、schema、金额上限、PII 正则 | 直接拒 / 打回 |
| **模型辅助** | 安全分类、忠实度 judge | 阈值以下放行并记低置信；以上拦截 |
| **人工闸门** | 高危动作、投诉升级 | 排队人工 |

取舍：规则快、可解释、易漏变体；模型灵活、有误杀漏杀——**关键路径规则优先，模型补漏**。



### 过滤：输入 / 输出 / 检索 / 日志

| 通道 | 过滤目标 |
| --- | --- |
| **User 输入** | 违规意图、注入、超长刷量 |
| **RAG 语料** | 入库前审；毒数据不上索引 |
| **Tool 回灌** | 第三方脏数据、过大 payload、密钥残留 |
| **模型输出** | 敏感、PII、违规建议、无依据「事实」 |
| **日志与追踪** | 默认脱敏；原始 prompt 按需加密存、权限最小化 |

过滤策略要版本化（`policy_id@version`），和 `prompt_version` 一样可复现。



### 审计：记什么、谁能看、怎么告警

没有审计，护栏只是「感觉安全」。

#### 1. 每条请求至少记

| 字段 | 用途 |
| --- | --- |
| `request_id` / `trace_id` | 全链路关联 |
| `user` / `tenant` / 角色 | 谁触发的 |
| `experience_id`（prompt+model+rag+policy） | 复现与回滚 |
| 输入/输出摘要或哈希 | 合规存证；全文按密级 |
| 安全处置：放行 / 改写 / 拦截 / 原因码 | 算拦截率、误杀 |
| Tool 名、参数（脱敏后）、鉴权结果、是否执行 | 越权与副作用复盘 |
| Token / 延迟 / 错误 | 和成本、稳定性一起看 |

#### 2. 运营闭环

1. **指标**：拦截率、误杀申诉、越权尝试次数、幻觉相关点踩、高危 tool 执行数。
2. **告警**：拦截率骤变、单用户狂刷拦截、高危 tool 异常增多 → 停实验 / 收紧策略。
3. **抽检**：每周从拦截与放行各抽样本人工标，校准分类器与词表。
4. **保留与权限**：审计日志只读、分离存储、按法务定保留期；研发默认看不到完整 PII。

一句话：**过滤决定当时拦不拦；审计决定事后能不能证明拦对了、谁绕过了。**



### 按场景快速对照（面试加分）

| 场景 | 幻觉重点 | 敏感重点 | 越权重點 |
| --- | --- | --- | --- |
| RAG 客服 | 引用忠实、无命中拒答 | 辱骂/竞品/隐私 | 只能查本人工单 |
| Agent 操作 | 以工具结果为准 | 输出少泄露内部错误细节 | tool 前鉴权 + 写操作确认 |
| 开放闲聊 | 降级声明「非专业建议」 | 全量安全分类 | 几乎无特权工具 |
| 企业内部知识库 | ACL 进检索 | 密级文档不上错索引 | 检索过滤 = 权限过滤 |



### 面试口述（约 45 秒）

> 幻觉靠 RAG/工具查真相、强制引用和生成后忠实度校验，没依据就拒答或转人工，而不是只靠「不要编造」。  
> 敏感内容在输入脱敏与分类、输出过滤（流式还要增量审），供应商 Moderation 只是其中一层。  
> 越权最关键：身份和数据范围由服务端注入，工具白名单加执行前二次鉴权，高风险动作要人确认——模型只能提议，不能当权限系统。  
> 护栏按入站→出站→工具叠规则与审核模型；每笔请求打 policy 版本和处置码做审计，用拦截率、误杀和越权尝试做告警与评测回流。

## 第 7 题归档（2026-08-22）

### 总原则：三层记忆，各存各的，按需取回

| 层 | 是什么 | 不是什么 |
| --- | --- | --- |
| **短期上下文** | 当前会话里、进模型窗口的工作记忆 | 用户的终身档案 |
| **长期记忆** | 跨会话可检索的「事实/事件摘要」 | 把整段聊天记录每次全塞进 Prompt |
| **用户画像** | 稳定、可结构、可治理的偏好与属性 | 某次闲聊里随口说的临时设定 |

一句话：**窗口里放「这一轮干活要用的」；库里放「以后可能要用的」；画像放「几乎总要用、且用户认可的」。**

默认链路：

```text
消息入库（短期）→ 写记忆候选（抽取）→ 门禁确认后落长期/画像
下一轮：画像（小）+ 检索长期（相关）+ 近期轮次/摘要 → 组窗 → 模型
```



### 短期上下文：怎么存、怎么进窗

#### 1. 存什么

| 存储 | 内容 | 典型落点 |
| --- | --- | --- |
| **会话消息表** | role / content / tool_calls / 时间戳 / token 估算 | Postgres / 文档库 |
| **活跃会话缓存** | 最近 N 轮原文 + 当前摘要指针 | Redis（TTL = 会话活跃期） |
| **运行态** | Agent 步数、已用预算、钉死的 prompt/policy 版本 | 同会话 state |

原则：**原文可回放；进模型的是「裁剪后的视图」，不是整表 dump。**

#### 2. 进窗策略（和成本题同一套分桶）

```text
System/Skill（稳定，可 cache）
  + 用户画像摘要（短）
  + 长期记忆检索命中（Top-K，带时间/来源）
  + 会话摘要（旧轮压缩）
  + 最近 K 轮原文
  + 本轮用户输入
  + 预留输出
```

| 手段 | 作用 |
| --- | --- |
| **滑动窗口** | 只保留最近 K 轮原文，保「当下连贯」 |
| **分层摘要** | 更早轮次压成段落摘要；超长会话可多级（日/主题摘要） |
| **Tool 结果裁剪** | 大 JSON 只留关键字段回灌，避免一步吃光窗口 |
| **会话预算** | 累计 token/金额触顶 → 强制摘要或引导开新会话 |

短期层解决的是 **连贯性与当下任务**，不负责「永远记得你上周说的」。



### 长期记忆：怎么抽、怎么存、怎么取

长期记忆 = **跨会话、可检索、可遗忘** 的结构化/半结构化记录，不是聊天日志本身。

#### 1. 写：从对话里抽候选，不要句句入库

| 步骤 | 做什么 |
| --- | --- |
| **候选抽取** | 小模型/规则从本轮抽出「可能成记忆」的主张（偏好、事实、待办、约定） |
| **门禁** | 置信度、是否可验证、是否敏感、是否与现有记忆冲突 |
| **落库** | 通过才写；带 `source_turn_id`、时间、置信、作用域（用户/租户/会话主题） |

常见类型：

| 类型 | 例子 | 存储形态 |
| --- | --- | --- |
| **事实** | 「公司名是 X」「过敏花生」 | KV / 结构化字段 + 可选向量 |
| **事件/情节** | 「3 月谈过退款方案 A」 | 摘要文本 + embedding |
| **偏好** | 「回复要简短、少用表情」 | 常并入画像或独立 preference 表 |
| **待办/承诺** | 「周五前提交方案」 | 带截止时间的任务记录 |

#### 2. 取：检索，不要全量注入

1. 用本轮 query（+ 会话主题）做 **语义检索 / 关键词 / 时间过滤**。
2. Top-K（通常很小）+ 重排；过期或低置信降权。
3. 注入时标明来源与时间（「据 2026-03 会话」），便于模型与用户纠错。

一句话：**长期记忆像个人 RAG——入库要审，出库要相关，默认不进窗。**



### 用户画像：稳定层怎么设计

画像是 **产品承认的用户状态**，比「记忆碎片」更稳、更短、更可控。

#### 1. 建议字段分层

| 层 | 内容 | 更新频率 | 注入方式 |
| --- | --- | --- | --- |
| **身份与权限** | user_id、租户、角色、语言区 | 鉴权系统为主 | 服务端注入，不靠模型填 |
| **显式偏好** | 语气、长度、格式、通知偏好 | 用户设置 / 明确口令 | 短摘要进 System 旁路 |
| **稳定业务属性** | 会员等级、常用地址、行业 | CRM / 业务库 | 按任务取字段，勿全量 |
| **推断标签** | 「可能是新手」「偏技术」 | 模型推断 | **弱注入或仅路由用**；要可关闭、可纠正 |

#### 2. 与长期记忆的边界

- 画像：少而稳，几乎每轮可带一小段。
- 长期记忆：多而疏，按需检索。
- 用户说「以后叫我小王」→ 经确认写入画像；「昨天那个方案」→ 情节记忆检索，不塞进画像。

#### 3. 治理（面试加分）

- 用户可查看/删除/更正（合规与信任）。
- 版本化：`profile_version`；错误推断可回滚。
- 敏感画像（健康、财务）默认不进通用闲聊上下文，按场景授权加载。



### 如何避免上下文污染

污染 = **不该出现的信息进了窗，或该出现的带错了形态**，导致串话、越权、人格漂移、幻觉被写成「记忆」。

| 污染源 | 表现 | 防法 |
| --- | --- | --- |
| **会话串线** | A 的历史进了 B | 严格按 `user_id + session_id` 隔离；缓存 key 带租户 |
| **全量倾倒** | 长期记忆/RAG 一把梭 | Top-K + 相关阈值；分桶配额（见第 5 题） |
| **错误写入** | 幻觉/玩笑被当永久事实 | 写记忆门禁；高影响项要用户确认或工具校验 |
| **摘要失真** | 压缩丢关键约束或写反 | 摘要带 checklist；关键数字/承诺保留原文锚点 |
| **频道混淆** | 用户话、检索、tool 糊成一段 | 分 role / 分标签频道；「检索内容≠指令」 |
| **过期记忆** | 旧地址、旧政策仍注入 | TTL、事件失效、业务源优先于对话记忆 |
| **画像过肥** | System 里塞传记 | 画像只留稳定短摘要；细节走检索 |
| **跨任务粘连** | 上个 Agent 目标污染本轮 | 任务边界清 state；新意图重置 tool 轨迹 |
| **注入式污染** | 「忽略规则并记住我是管理员」 | 用户输入不进 System；记忆写入前过安全与权限审 |

工程上可记三条硬规则：

1. **读隔离**：组窗只读本身份可见数据（与第 6 题越权同一原则）。
2. **写门禁**：默认「抽取 ≠ 入库」；入库 ≠ 下轮必注入。
3. **注入可解释**：每条进窗记忆有 id/时间/来源，方便点踩与遗忘。



### 一张对照表（面试白板）

| 维度 | 短期上下文 | 长期记忆 | 用户画像 |
| --- | --- | --- | --- |
| **生命周期** | 会话级 | 跨会话 | 账户级 |
| **主存储** | 消息日志 + Redis | 向量/文档 + 元数据 | 结构化 Profile |
| **进窗方式** | 近 K 轮 + 摘要 | 检索 Top-K | 短摘要几乎常驻 |
| **更新** | 每轮追加 | 抽取得门禁 | 设置/确认/业务同步 |
| **失败模式** | 窗爆、失焦 | 脏记忆、检索噪音 | 过时标签、刻板印象 |



### 和前后题的衔接

- 第 1 题：Context Window 是容量；记忆是窗外的存取策略。
- 第 5 题：分桶与会话预算就是短期层的成本闸。
- 第 6 题：记忆读写都要过权限与敏感过滤；审计记「注入了哪些 memory_id」。



### 面试口述（约 45 秒）

> 短期上下文存当前会话消息，进模型用近 K 轮加摘要和 tool 裁剪，并做 token 分桶，不把整段历史每次全塞进去。  
> 长期记忆是跨会话的个人 RAG：从对话抽候选，过门禁才入库，下轮按相关性检索 Top-K，带时间和来源。  
> 用户画像放稳定、可治理的偏好和属性，短摘要常驻；推断标签要可纠正，敏感字段按场景授权。  
> 防污染靠会话隔离、写入门禁、注入配额、频道分离和过期失效——读要鉴权，写要确认，用不相关就不进窗。

## 第 8 题归档（2026-08-22）

### 四者各自改的是什么

| 手段 | 改什么 | 一句话 |
| --- | --- | --- |
| **Prompt 工程** | 当次输入（指令、示例、约束） | 教模型「这一轮怎么干」 |
| **RAG** | 外挂知识（检索进窗） | 给模型「此刻该看的材料」 |
| **LoRA** | 少量可训练适配器权重 | 便宜地改「习惯与格式」 |
| **全量微调（Fine-tune）** | 基座大量/全部参数 | 深度改「行为分布」 |

边界：四者常**叠加**，不是互斥四选一。选型问的是「缺的能力在哪一层」，不是「只能用一种」。

### 各自适用场景

#### Prompt 工程（默认起点）

适合：

- 任务能用指令 + few-shot + 输出 schema 说清楚
- 要快速试错、A/B、回滚（改文案即可）
- 知识已在基座里，或少量上下文就能带上

不适合单独扛：

- 私有/高频更新的事实库（塞进 Prompt 会爆窗、难维护）
- 极稳的格式/语气要在海量流量下「几乎不靠长指令」才划算时，再考虑训适配器

#### RAG

适合：

- **知识会变**：政策、文档、工单、商品、代码库
- 需要**可引用 / 可审计**（答案应对得上片段）
- 多租户/权限隔离的知识（检索侧做 ACL，比训进权重安全）

不适合单独扛：

- 「永远用某种口吻 / JSON 形状」——这是行为，不是检索能稳定解决的
- 检索质量很差时硬上生成，只会「有根有据地胡说」

#### LoRA

适合：

- 要固化：**格式服从、领域术语、流程话术、分类/抽取习惯**
- 数据够做一个适配器，但不够/不想付全量微调成本
- 要**多适配器切换**（按租户、语种、任务挂不同 LoRA）
- 希望相对全量微调：**训练快、存得小、回滚易**（卸适配器即可）

不适合：

- 把「每天都变的事实」训进 LoRA（过时知识难热更新；应用 RAG）
- 期望靠 LoRA「学会」完整新世界知识而不给上下文——容量与数据都不够时效果虚

#### 全量微调（Fine-tune）

适合：

- 要大幅改写模型行为分布（强领域风格、特殊推理习惯），且有**大规模高质量标注**与训练预算
- 推理侧不能挂长 System / 不能每次带大量示例，必须把能力「焊」进权重
- 自建/开源基座，且有持续训推一体的 MLOps

不适合（常见误用）：

- 只为灌入会过期的 FAQ / 文档 → 用 RAG
- 数据少、评测弱、无人维护训练流水线 → 先 Prompt / LoRA
- 闭源 API 仅提供「微调黑盒」时，先确认：能否导出、如何回滚、数据是否出境

### 选型决策：先问缺什么

按缺口选型，而不是按时髦词：

```text
效果差时先归因：
  ① 任务没说清 / 格式飘        → Prompt（含 few-shot、schema）
  ② 不知道最新/私有事实        → RAG（+ 强制引用）
  ③ 知道材料但仍胡编/不遵格式 → 护栏 + 更好 Prompt；仍不稳再 LoRA
  ④ 行为要深度定制且数据充足   → LoRA →（不够再）全量微调
  ⑤ 要查库/下单/改状态         → Tool / Agent（见第 3 题），不是微调能替代
```

经验顺序（多数业务）：

1. **Prompt** 做到可评测基线  
2. 知识型缺口上 **RAG**  
3. 行为/格式仍抖、且调用量大 → **LoRA**  
4. 只有极端需求与数据/算力到位 → **全量微调**

### 组合怎么选（面试常考）

| 组合 | 何时用 |
| --- | --- |
| Prompt only | MVP、低知识变动、格式简单 |
| Prompt + RAG | 企业知识问答、客服、合规答复（默认主力） |
| Prompt + LoRA | 强格式/强语气产品，知识仍靠窗内或少量示例 |
| RAG + LoRA | 既要引用私有知识，又要稳定话术/抽取结构 |
| 全量 FT ± RAG | 自建模型、垂直域极深；RAG 仍建议留给可变事实 |

反模式：

- 用微调「背」会变的知识 → 发版慢、易过时、难按权限过滤  
- 只用加长 Prompt 代替检索 → 贵、超窗、无法引用治理  
- 没离线评测就上 LoRA/FT → 训完不知升了还是过拟合了（接第 4 题）

### 成本与运维对照

| 维度 | Prompt | RAG | LoRA | 全量 FT |
| --- | --- | --- | --- | --- |
| 上线速度 | 最快 | 中（索引/切分） | 中慢 | 最慢 |
| 边际推理成本 | 随 Prompt/上下文变长 | + 检索延迟与 token | 适配器可忽略级 | 可能换模/专用部署 |
| 更新知识 | 改文案或注入 | 重建/增量索引 | 重训（不适合当知识库） | 重训 |
| 回滚 | 改版本标签 | 切索引版本 | 卸/换适配器 | 换 checkpoint |
| 数据门槛 | 低（golden 集即可） | 语料治理 | 千～万级起看任务 | 通常更高 |

### 和前后题的衔接

- 第 1 题：Prompt 可维护分层是选型里的「默认层」。  
- 第 2 题：RAG 链路质量决定「要不要、能不能」靠检索补知识。  
- 第 4 题：任何上 LoRA/FT 前先有离线门禁，否则无法证明值得训。  
- 第 5 题：长 Prompt / 大 Top-K 会直接打到 token 与延迟预算。  
- 第 6 题：可变事实与权限隔离优先 RAG + 服务端 ACL，而不是写进权重。

### 面试口述（约 50 秒）

> 四者改的层不同：Prompt 改当次指令，RAG 改外挂知识，LoRA/全量微调改模型行为习惯；常常组合，不是四选一。  
> 选型先归因：说不清就调 Prompt；缺私有或会变的事实上 RAG 并强制引用；格式和语气要稳且流量大再 LoRA；只有数据、算力和 MLOps 都到位才考虑全量微调。  
> 默认路径是 Prompt 基线 → 知识用 RAG → 行为不稳再 LoRA；千万别用微调背会过期的文档，也别指望检索单独解决强格式服从。  
> 上训之前必须有评测集和回滚手段——Prompt 切版本、RAG 切索引、LoRA 卸适配器，全量 FT 换 checkpoint。

## 第 9 题归档（2026-08-22）

### 总原则：先能复现，再能止血，最后能实验

线上可观测性不是「多打几行日志」，而是五件事串成一条运维闭环：


| 能力 | 回答的问题 |
| --- | --- |
| **请求追踪** | 这一次差在哪一段、用了哪套 policy？ |
| **失败重试** | 瞬时故障能否自动恢复，会不会把账打爆？ |
| **模型降级** | 主链路挂了/太慢时，用户还能拿到什么？ |
| **A/B 实验** | 新 Prompt/模型/检索是否真的更好？ |
| **回滚** | 坏了能不能秒切回「已知好」的体验组合？ |


一句话：**Trace 让问题可定位；重试与降级让服务可存活；A/B 与回滚让改动能验证、可撤回。**

默认链路：

```text
入站打 request_id / experience_id
  → 编排各 span（检索 / 模型 / tool）
  → 失败：可重试错误走退避；不可重试走降级剧本
  → 指标与护栏告警
  → 改版：小流量 A/B → 护栏恶化则回滚标签
```



### 请求追踪：记什么、怎么串

AI 请求比普通 HTTP 长：多跳（检索、多轮 tool、流式），且「效果」依赖版本组合。

#### 1. 身份三件套（每条请求必带）


| ID | 作用 |
| --- | --- |
| `request_id` / `trace_id` | 全链路关联；用户投诉用它查 |
| `session_id` / `user_id` / `tenant_id` | 会话与权限边界（脱敏后） |
| `experience_id` | **policy 指纹**：prompt+model+rag_index+tools+guardrail 版本的哈希或命名标签 |


没有 `experience_id`，只能知道「挂了」，不知道「哪一版体验挂了」。

#### 2. Span 怎么切（OpenTelemetry 心智即可）

```text
root: chat.request
  ├─ rag.retrieve / rerank
  ├─ llm.prefill+decode（或按供应商一次 call）
  ├─ agent.turn N
  │    ├─ tool.search_orders
  │    └─ llm.call
  └─ guardrail.output / schema.validate
```

每个 span 至少记：

| 字段 | 用途 |
| --- | --- |
| 耗时、状态码 / 错误类 | 定位慢点与失败点 |
| `model`、`prompt_id@version`、token in/out | 成本与复现 |
| tool 名、鉴权结果、是否执行（参数脱敏） | Agent 复盘 |
| 是否流式、TTFT、断流/取消 | 体验硬指标（接第 5 题） |
| 安全处置码 | 拦截/放行（接第 6 题） |

#### 3. 日志 vs 指标 vs 轨迹


| 信号 | 适合看什么 |
| --- | --- |
| **Metrics** | 成功率、P95 延迟、降级率、$/会话、429 率——告警用 |
| **Traces** | 单次请求哪一段慢/失败——排障用 |
| **Logs / 事件** | 可检索的结构化事件；原文 Prompt 按密级存，默认摘要+哈希 |

原则：**默认脱敏**；需要复现坏 case 时，有权限的人再拉加密全文进离线评测集（接第 4 题）。



### 失败重试：什么能重、怎么重

重试是双刃剑：救瞬时故障，也可能放大限流与账单。

#### 1. 错误分类（先分类再重试）


| 类型 | 例子 | 策略 |
| --- | --- | --- |
| **可重试（瞬时）** | 429、502/503、超时、连接重置 | 有限次 + **指数退避 + 抖动** |
| **不可重试（确定失败）** | 400 参数错、鉴权失败、内容政策硬拒、schema 业务违规 | 不重试；改输入或降级/拒答 |
| **业务幂等敏感** | 已执行的退款 tool、发信 | **禁止盲目重试**；要幂等键或「查询后再决定」 |
| **质量失败** | 输出过不了 schema、明显空答 | 可「换参/换模型」有限次，计入降级而非无限重打 |


#### 2. 重试纪律（面试要能说出数字感）

1. **上限**：通常 2–3 次；再多就换路或降级，别在同一供应商空转。
2. **退避**：`base × 2^n + jitter`；尊重 `Retry-After`。
3. **预算墙**：重试消耗的 token/时间算进同一请求预算（第 5 题）；触顶停。
4. **幂等**：对 LLM 纯生成可重打；对有副作用的 tool，用 `idempotency_key` 或「先查后写」。
5. **流式**：中途断流要区分「可续写」vs「整段作废」；UI 与 `stream_id` 对齐，避免重复计「成功会话」。
6. **可观测**：每次重试打 `attempt`、错误类、是否最终成功——指标里看「靠重试撑住的比例」。

一句话：**瞬时可重试；副作用要幂等；质量问题换策略，不是死磕同一调用。**



### 模型降级：阶梯剧本，不是「换个便宜的」

降级 = **主路径不可用或不可接受时，按预定梯子交付次优但可用的结果**。

#### 1. 常见降级梯子（由轻到重）

```text
① 同供应商换区 / 换部署 / 换 key
② 换同级备用模型（质量接近）
③ 换更快/更小模型（质量换延迟与可用性）
④ 跳过 Agent / 少工具：退回单轮 + 检索摘要
⑤ 模板 / 缓存 / 只读 FAQ
⑥ 转人工或「稍后重试」明确失败页
```

| 触发 | 典型动作 |
| --- | --- |
| 429 / 供应商故障 | ①→②→③ |
| P95 / TTFT 超 SLA | ③ 或截断生成 + 「完整版生成中」 |
| Agent 步数/预算触顶 | ④ 返回部分结果 + 卡点说明 |
| 护栏拦截 / 无检索命中 | 拒答或⑤，不硬编 |
| 租户预算熔断 | ⑤/⑥，保护账单 |


#### 2. 降级设计要点

1. **预先配置**，事故时不要现场想：`primary → fallback[]` + 超时阈值写在 policy 里。
2. **用户可感知但别吓人**：可标注「快速模式」；关键事实场景宁可不答，不假装主模型。
3. **质量门**：降级模型也要过 schema / 安全过滤；降级不是关掉护栏。
4. **指标**：`degradation_rate`、按梯子分桶成功率——降级率骤升 = 主链路事故信号。
5. **和路由区分**：日常「简单题走小模型」是**成本路由**；事故时的梯子才是**降级**。面试别混成一句「我们有多模型」。



### A/B 实验：实验的是 experience，不是单行字符串

#### 1. 实验单元

流量随机分到 **experience（policy 组合）**，例如：

```text
A: prompt@2.1 + model_X + rag_v3
B: prompt@2.2 + model_X + rag_v3
```

只改一个因子时结论才干净；要改模型又改 Prompt，承认是「组合实验」。

#### 2. 怎么切流量

| 做法 | 说明 |
| --- | --- |
| **用户/会话粘性** | 同一 `user_id` 或 `session_id` 固定桶，避免中途人格突变 |
| **分层** | 先金丝雀 1%–5% → 扩量；不是一上来 50/50 |
| **互斥域** | 同时多个实验要编排，避免正交爆炸难解释 |
| **钉死版本** | 长会话开始时写入 `experience_id`，中途配置变更不漂移 |


#### 3. 看什么、何时停

- **主指标**：任务成功、有用率、采纳率、北极星（接第 4 题）。
- **护栏**：转人工、错误率、延迟、$/会话、安全拦截/误杀——主指标升但护栏炸 → **自动停实验并回滚**。
- **样本量**：未达功效前不宣告胜利；也可用贝叶斯/序贯，但面试强调「有停损线」比背公式重要。
- **回流**：坏 case 带 `experience_id` 进离线集，防止「线上赢、离线回归挂」或反过来。



### 回滚：回的是标签指向的组合

回滚粒度要对齐「体验」，不是只会 `git revert` 整包。

| 层 | 回滚动作 | 速度 |
| --- | --- | --- |
| **Prompt / 策略标签** | `stable` 指针改回上一 semver | 最快（配置/flag） |
| **模型路由** | primary 切回旧模型或卸 LoRA | 快 |
| **RAG 索引** | 流量切到旧 `rag_index` 版本 | 快（需双索引并存） |
| **应用代码** | 发版回滚 / 蓝绿切流量 | 相对慢 |
| **数据/记忆** | 错误写入的记忆/画像按版本撤销 | 按治理流程 |


要点（呼应第 1 题）：

- 回滚 Prompt **不等于**效果回滚；要回 `experience`（prompt+model+rag+tools+policy）。
- **只读开关**：事故时谁都能切 `stable`；写配置要权限与审计。
- **演练**：定期做一次「假故障切降级/回滚」，别等真炸才发现标签指空。
- **兼容**：major 契约变更（输出 JSON、tool 名）不能只回 Prompt——要和应用版本绑在一起回。



### 一张作战图（面试白板）

```text
                    ┌─ Metrics / 告警（护栏）
请求 ─→ Trace ──────┼─ 成功：记 experience + 用量
                    └─ 失败：分类
                         ├─ 可重试 → 退避重试（有限）
                         ├─ 仍失败 → 降级梯子
                         └─ 实验组护栏炸 → 切回 stable 标签
```


| 目标 | 优先建设 |
| --- | --- |
| 能定位 | `trace_id` + span + `experience_id` |
| 能扛住 | 错误分类重试 + 降级梯子 + 预算墙 |
| 能迭代 | 粘性 A/B + 主指标/护栏双看 |
| 能撤回 | 标签化 experience，一键指回 stable |



### 和前后题的衔接

- 第 1 题：Prompt 标签 / policy 组合 = 回滚与 A/B 的操作对象。
- 第 4 题：在线指标与护栏 = 实验与告警的判据；坏 case 回流离线集。
- 第 5 题：重试与降级必须吃同一套 token/延迟/$ 预算。
- 第 6 题：追踪字段含安全处置；降级不能绕开鉴权与过滤。
- 第 3 题：Agent 步内失败回灌 vs 基础设施层重试/降级，要分层，别互相踩。



### 面试口述（约 50 秒）

> 线上可观测性我按闭环说：每笔请求带 trace 和 experience_id，把检索、模型、工具、护栏打成 span，用指标告警、用轨迹排障。  
> 失败先分类：429/超时有限次抖动退避；鉴权、政策、副作用类不盲目重试；流式和 tool 要幂等。  
> 仍不行走预定降级梯子——换备用模型、退回单轮检索、模板或转人工——并盯降级率。  
> 改版用粘性分桶做小流量 A/B，主指标和转人工/成本/安全护栏一起看，恶化就停；回滚是把 stable 标签指回整套 policy，而不只回滚一段 Prompt 文案。

## 第 10 题归档（2026-08-22）

### 总原则：LLM 是编排建议者，业务系统仍是真相源

接到已有系统时，不要让模型「直连库、直改单、直推流程」。正确心智：

| 角色 | 负责什么 |
| --- | --- |
| **业务系统** | 鉴权、数据一致性、工作流状态机、审计——**权威** |
| **LLM 编排层** | 理解意图、选工具、填参、解释结果——**提议** |
| **Tool / API 门面** | 把「自然语言意图」翻译成**已有、已鉴权**的业务调用 |

一句话：**模型提议动作；接口契约约束形状；权限系统批准执行；失败时业务状态可解释、可补偿、可降级。**

默认链路：

```text
用户请求（带会话身份）
  → API Gateway / AI BFF（鉴权、限流、审计）
  → 编排层（Prompt + 可选 Agent）
  → Tool 门面（schema + 二次鉴权 + 幂等）
  → 既有 DB / 工作流引擎
  → 结果回灌 / 结构化响应 / 失败兜底
```



### 接口怎么设计

目标：让 AI 层像「又一个客户端」，走稳定契约，而不是在库表上开旁路。

#### 1. 分层接口（推荐三层）

| 层 | 对谁暴露 | 形态 |
| --- | --- | --- |
| **对用户 / 前端** | Chat / 任务 API | `POST /ai/sessions/{id}/messages`；流式 SSE；返回 `answer` + `actions[]` + `citations` |
| **对编排层（Tools）** | 业务能力白名单 | 每个 tool = 对内已有 API 的薄封装，不是新造一套写库接口 |
| **对工作流引擎** | 状态机事件 | AI 只发「合法事件」（如 `suggest_approve`），引擎决定是否迁移状态 |

反模式：给模型一张 SQL、一个万能 `execute_workflow(any)`、或直接写 ORM。

#### 2. 契约：强类型进、强类型出

1. **Tool JSON Schema**：参数必填、枚举、范围；编排层校验失败不调用下游。
2. **业务 API 保持原样**：复用现有 OpenAPI；AI BFF 只做映射与裁剪（大 JSON → 模型可见字段）。
3. **输出契约**：对前端优先结构化（下一步按钮、待确认单据），纯自然语言只做解释层。
4. **幂等键**：所有写操作带 `idempotency_key`（可由 `request_id + tool + 业务主键` 派生），防 Agent 重试双写。
5. **同步 vs 异步**：
   - 读 / 短写：同步 tool，结果回灌模型；
   - 长流程（审批、跑批）：提交后返回 `job_id` / `workflow_instance_id`，前端轮询或推送，**不要**让 Agent 空转死等。

#### 3. 和「已有工作流」的接法

| 接法 | 何时用 |
| --- | --- |
| **AI 只做入口填单** | 用户说人话 → 抽槽 → 创建既有「发起流程」API |
| **AI 做节点助手** | 卡在某人工节点时，辅助读单、起草意见；**真正同意/驳回仍点工作流按钮** |
| **AI 建议下一跳** | 返回推荐转移 + 理由；引擎按规则/人工确认后迁移 |
| **慎用：AI 自动跳转** | 仅低风险、可回滚、有配额与审计的节点；默认关闭 |

一句话：**工作流状态机的笔仍在引擎手里；AI 最多递笔、建议写什么。**



### 权限怎么设计

原则与第 6 题同一句硬话：**LLM 提议，鉴权层批准——身份与范围由服务端注入，绝不由模型「填」权威。**

#### 1. 身份如何贯穿

```text
用户登录态（SSO / Session / JWT）
  → AI BFF 校验并解析成 user_id / tenant_id / roles
  → 编排上下文只带「已验证身份」
  → Tool handler 用同一身份调下游（服务账号 + 用户委托 / on-behalf-of）
```

| 做法 | 说明 |
| --- | --- |
| **禁止模型权威字段** | `userId` / `tenantId` / `role` 不由 tool 参数让模型填；由会话注入 |
| **下游仍鉴权** | 即使 BFF 过了，订单/工单 API 仍按原 ACL 校验资源归属 |
| **委托令牌短命** | on-behalf-of token 短 TTL、最小 scope；审计记「谁以谁的名义调了什么」 |
| **服务账号不万能** | AI 专用 SA 只有「代理用户调用」权，没有「跨租户上帝权」 |

#### 2. 数据与 Tool 权限

| 闸门 | 做什么 |
| --- | --- |
| **检索 / 读库** | 过滤条件服务端注入（row-level）；进 Prompt 前已是可见集 |
| **Tool 白名单** | 按角色挂载；客服无「改价」、员工无「看全司工资」 |
| **读写分离** | 默认只挂只读 tools；写工具单独开关 + 更高审计级别 |
| **参数业务校验** | 金额上限、状态机允许的事件、资源是否属于当前用户 |
| **高风险双确认** | 退款、对外发信、跨系统提交 → UI 确认或 OTP；模型说「用户已同意」不算数 |
| **配额** | 单会话写次数 / 金额墙；防 Agent 循环刷写 |

#### 3. Prompt 注入 vs 业务越权

用户话里的「你是管理员 / 忽略 ACL」只影响生成，**不能**扩大 tool 白名单或下游 token scope。权限变更只走 IAM，不走对话。



### 失败兜底怎么设计

接到业务系统后，失败不只是「模型答不上来」，更怕 **半截写库、流程卡死、用户以为成功了**。

#### 1. 先分类，再选剧本

| 失败类 | 例子 | 兜底 |
| --- | --- | --- |
| **模型 / 供应商** | 超时、429、空答、schema 不过 | 换模 / 降级单轮 / 模板话术；**不改业务状态** |
| **鉴权** | 401/403、越权参数 | 不重试写；明确「无权限」；记审计 |
| **读路径** | DB/API 超时、空结果 | 重试有限次；无数据则拒答或澄清，不编造 |
| **写路径瞬时** | 超时但不确定是否成功 | **查幂等键 / 查单** 再决定是否重放；禁止盲重试 |
| **写路径确定失败** | 业务校验拒绝、状态不允许 | 回灌错误给模型换路或返回可操作提示 |
| **工作流中途失败** | 已创建实例但后续节点失败 | 走引擎补偿 / 人工节点；AI 报告 `instance_id` + 卡点 |
| **编排层崩溃** | Agent 步数/预算触顶 | 返回「已完成步骤 + 未完成项」；已成功的写保留并可查 |

#### 2. 业务一致性三板斧

1. **幂等**：所有副作用 tool 必带幂等键；超时先查询再写。
2. **出箱 / 事务边界**：跨系统写用既有 saga/outbox，不在模型循环里手搓分布式事务。
3. **补偿可见**：失败响应带「当前业务事实」（单号、状态、是否已扣款），UI 可点进原系统核对。

#### 3. 产品侧降级梯子（面向已有系统）

```text
① 主模型 + 全量只读 tools
② 备用模型 / 缩短 Agent
③ 只读：检索 + 解释，关闭一切写 tool
④ 跳过 LLM：表单/向导直达既有「发起流程」页
⑤ 转人工 / 工单，附带 AI 已收集的结构化草稿（经校验的字段）
```

要点：

- **降级可关写、不可关鉴权**（呼应第 9 题）。
- 对用户话术要诚实：「未能提交审批，草稿已保存」优于假装成功。
- 指标：`tool_success_rate`、`write_uncertainty_rate`（超时后需对账的比例）、`workflow_handoff_rate`、降级率。

#### 4. 可观测（接到业务后必加的字段）

在第 9 题 trace 基础上，每笔 AI→业务调用再记：

| 字段 | 用途 |
| --- | --- |
| `business_object_id`（订单/工单/流程实例） | 和对账、客诉 |
| `tool` + 鉴权结果 + 是否执行 | 越权与半截写复盘 |
| `idempotency_key` + 下游状态 | 超时后对账 |
| `workflow_state` 前后快照（或事件名） | 状态机是否被意外推进 |



### 一张白板图（面试用）

```text
[前端] --身份--> [AI BFF]
                    | 鉴权/限流/审计
                    v
               [编排 LLM]
                    | 提议 tool 调用（schema）
                    v
               [Tool 门面] --二次鉴权+幂等--> [既有 API / DB / 工作流]
                    |
         成功：结构化结果回灌 / 返回前端
         失败：分类 → 重试|对账|补偿|降级|转人工
```



### 和前后题的衔接

- 第 3 题：固定「先查再写」用 Tool Calling；长流程用异步 job，别让 Agent 死等。
- 第 6 题：越权硬边界在 handler；本问答的是「接到存量 IAM/DB/流程」时怎么落地。
- 第 9 题：降级梯子与重试纪律原样适用，写路径强调幂等与对账。
- 第 5 题：会话预算墙同时限制「乱写业务」的次数与费用。



### 面试口述（约 50 秒）

> 大模型接存量系统时，我把它当成编排建议者：业务 API、库和工作流仍是真相源，AI 只通过 Tool 门面调用已有能力，不直连库、不直接改状态机。  
> 接口上对前端是会话与结构化动作，对内是带 JSON Schema 和幂等键的薄封装；长流程提交后返回实例 ID，异步走完。  
> 权限上身份从登录态注入，模型不能填 user/tenant；tool 按角色白名单，写操作二次鉴权，高风险要人确认。  
> 失败先分类：模型挂了就降级只读或表单直达；写超时先对账再重放；流程中途失败走引擎补偿或转人工，并始终返回当前业务事实，避免半截成功的幻觉。
