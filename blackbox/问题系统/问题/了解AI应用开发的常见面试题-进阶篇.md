# 了解AI应用开发的常见面试题（进阶篇）

> 与 [了解AI应用开发的常见面试题](了解AI应用开发的常见面试题.md) 互补：上一篇偏 Prompt / RAG / Agent / 评估 / 成本 / 护栏 / 记忆 / 选型 / 可观测 / 接业务；本篇偏工程落地、架构取舍与产品化细节。

1. 向量库怎么选型？过滤（metadata filter）、混合检索（关键词 + 向量）、ANN 参数各自影响召回与延迟，你会怎么压测？
2. 结构化输出（JSON Schema / Function Calling / Constrained Decoding）怎么保证可解析？解析失败时的重试、修复与降级怎么设计？
3. 多模型路由怎么做？按难度、成本、延迟、安全分级分流时，入口分类器与回退策略怎么配，如何避免路由本身成为瓶颈？
4. 语义缓存（Semantic Cache）适合什么场景？相似度阈值、失效策略、与业务正确性的冲突怎么处理？
5. 多租户 AI SaaS 如何隔离：数据、索引、配额、密钥与 Prompt 策略？租户定制模型/知识库时怎么防串租？
6. 人机协同（Human-in-the-loop）在哪些节点必须介入？草稿确认、高风险动作审批、坏 case 标注回流怎么做成可运营流程？
7. 多模态应用（图文 / 语音 / 文档解析）和纯文本链路差在哪？模态对齐、长文档切页、ASR 误差对下游 Agent 的影响怎么兜？
8. 多 Agent / 工作流编排（顺序、并行、辩论、主管-工人）何时比单 Agent 更合适？状态共享、失败隔离与可观测怎么设计？
9. AI 应用的 CI/CD 和传统服务有何不同？评测集门禁、Prompt/索引/模型版本、金丝雀与「体验回滚」如何进流水线？
10. 开源模型自建 vs 闭源 API：合规、成本、效果、运维怎么权衡？混合部署（敏感走私有、通用走 API）的边界怎么划？

## 第 1 题归档（2026-08-22）

### 选型：先定约束，再比产品

向量库不是「哪个 ANN 最快」的单选题，而是 **检索契约 × 数据规模 × 运维边界** 的组合题。


| 维度 | 先问清什么 | 选型落点 |
| --- | --- | --- |
| **过滤能力** | 租户/权限/时间/标签是否每查必带？过滤选择性高还是低？ | 要 pre-filter / 强过滤一致性 → 优先支持原生 metadata + 过滤下 ANN 的库 |
| **混合检索** | 专有名词、编号、错误拼写多不多？纯语义是否经常漏？ | 需要 BM25/稀疏向量同引擎 → 看是否内置 hybrid，还是自建 ES + 向量库双路 |
| **规模与延迟** | 百万 / 千万 / 亿级？P95 目标多少 ms？QPS？ | 内存型（如 HNSW 常驻）vs 磁盘/量化；托管 API vs 自建 |
| **一致性与写入** | 实时入库？批量重建？删除/更新频率？ | 近实时索引 vs 批重建；软删与 tombstone 成本 |
| **多租户** | 按 collection 拆还是 metadata 隔离？ | 隔离强度 vs 索引碎片；见进阶第 5 题 |
| **运维** | 谁值班、是否要 VPC/私有化、备份与版本？ | pgvector/自建 vs Pinecone/云厂商托管 |
| **生态** | 是否已有 Postgres / ES / 云账号？ | 能复用现有栈时，少引入一套新状态服务 |

常见落点（面试口述用「场景映射」，少背品牌榜）：

- **已有 Postgres、百万级内、要事务同仓**：pgvector 够用；复杂 hybrid 可外挂全文。
- **强过滤 + 混合 + 托管少运维**：看云向量库 / 专用向量服务是否原生支持 filter + sparse。
- **亿级、延迟紧、可接受运维**：自建 Milvus / Qdrant / Weaviate 等，按过滤与 hybrid 成熟度比。
- **只要语义、过滤弱、快速试点**：轻量库或托管；别一上来上分布式。

一句话：**先写清「必带 filter 的查询占比、是否要 hybrid、规模与 P95」三张表，再选引擎；品牌是结果不是起点。**



### 三者各自怎么动召回与延迟

#### 1. Metadata filter

| 实现路径 | 对召回 | 对延迟 | 典型坑 |
| --- | --- | --- | --- |
| **Pre-filter**（先缩候选再 ANN） | 正确时召回准；过滤字段漏标/错标 → 真相关被裁掉 | 选择性高（很少文档匹配）时快；选择性低时几乎等于全库扫 | 权限漏过滤 = 串租；过度过滤 = 空结果 |
| **Post-filter**（先 ANN 再滤） | Top-N 被滤光 → **假低召回**（相关的根本没进候选） | ANN 本身稳，但有效命中变少，常要加大 `ef`/`top_k` 补洞 → 延迟↑ | 「看起来索引挺快，业务却说搜不到」 |
| **Filter-aware ANN**（图/倒排感知约束） | 理想上兼顾 | 依赖实现质量 | 各引擎差异大，必须用**带 filter 的评测集**验证 |

面试要点：过滤不是免费的；**post-filter + 小 top_k 是召回杀手**。权限类过滤必须 pre 或引擎保证「过滤下的近似正确」，不能事后碰运气。

#### 2. 混合检索（关键词 / 稀疏 + 向量 / 稠密）

| 路径 | 召回影响 | 延迟影响 |
| --- | --- | --- |
| **稠密向量** | 同义、改写、跨语言强；专名、货号、罕见词弱 | 单路 ANN，延迟相对可控 |
| **稀疏 / BM25** | 精确词、编号、标题命中强；同义弱 | 倒排通常很快；大词表/长 query 有成本 |
| **Hybrid + 融合**（RRF / 加权 / 学习排序前融合） | 两路互补，整体 Recall@K 常升；融合权重不当会互相拖累 | **两路并行**时延迟≈max(两路)+融合；串行则相加；还要多一次重排时再叠 |

何时上 hybrid：评测集上「专名/编号类」问句，纯向量 Recall 明显差于 BM25；或用户 query 短、实体密。  
何时先不上：语料同质、问法口语化、专名少——多一路只加复杂度和调参面。

#### 3. ANN 参数（以 HNSW / IVF 常见旋钮为例）

| 参数族 | 调大时 | 调小时 |
| --- | --- | --- |
| **构建期**（HNSW `M`、IVF `nlist`） | 图/倒排更密 → 查询上限更高、索引更大、构建更慢 | 省内存/构建，但查询再猛也难补回结构损失 |
| **查询期**（HNSW `ef_search`、IVF `nprobe`） | 探更多节点 → **召回↑、延迟↑、CPU↑** | 延迟好、易漏近邻 |
| **量化**（PQ / SQ / 二进制） | 内存↓、吞吐↑；距离近似 → 召回常降，靠更大候选 + 精排补 | 全精度相反 |
| **候选深度 top_k / 重排窗** | 给 Reranker 的材料多 → 端到端质量可能升 | 省延迟；rerank 救不了「没召回进窗」 |

一句话：**构建参数定天花板，查询参数在天花板下买延迟；量化用空间/吞吐换召回，要用更大候选补。**



### 压测怎么做（质量压测 + 性能压测拆开）

不要只打 QPS；向量检索的「压垮」经常是 **带 filter 的召回塌了**，而不是 CPU 满了。

#### A. 质量基线（先有数再谈快）

1. **评测集**：真实 query；标注相关 chunk id；按场景打标（专名、口语、多跳、带租户/时间过滤）。
2. **对照臂**：暴力/精确 Top-K（或高 `ef` 近精确）作 upper bound；纯向量 / 纯 BM25 / hybrid 三路。
3. **指标**：Recall@K、MRR/nDCG；**带 filter 的子集单独报**；记录空结果率。
4. **扫参**：固定 K，扫 `ef_search`/`nprobe`、hybrid 权重、候选窗；画出 **Recall–Latency Pareto**，选工作点而非单点最优。

#### B. 性能与容量

| 测什么 | 怎么造负载 | 看什么 |
| --- | --- | --- |
| **延迟** | 生产 trace 重放；或按 filter 选择性分层（高/中/低匹配率） | P50/P95/P99；按「有无 filter / 是否 hybrid」分桶 |
| **吞吐** | 阶梯加压到目标 QPS，再过量找拐点 | QPS–P95 曲线；CPU、内存、磁盘 IOPS |
| **写入干扰** | 查询稳态时叠插入/更新/删除 | 查询尾延迟是否抖；索引 lag |
| **冷热** | 冷启动、缓存击穿、大租户热点 | 首查 vs 稳态；是否单租户拖垮 |
| **失败态** | 超时、限流、副本故障 | 降级是否仍返回可用结果（如关 hybrid、降 ef） |

#### C. 实验纪律

- **钉版本**：embedding 模型、index 构建参数、数据快照、query 集哈希一起记进报告。
- **端到端与组件分开**：组件 = 向量库耗时；端到端 = + embedding + rerank + LLM。优化前先看火焰图在哪段。
- **SLA 写法**：例如「租户过滤下 Recall@20 ≥ 0.85，检索 P95 ≤ 80ms @ 200 QPS」——三位一体，缺一不可上线。

### 面试口述（约 50 秒）

> 选型我先定三件事：查询是否必带强过滤、要不要关键词混合、规模和 P95。再决定托管还是自建、能否复用 Postgres/ES。  
> Filter 上，post-filter 加小 top_k 最容易假低召回；权限类必须 pre-filter 或引擎保证过滤下近似正确。Hybrid 用在专名/编号上补稠密的短板，两路并行看融合，延迟按更慢那路算。ANN 构建参数定天花板，`ef`/`nprobe` 用延迟换召回，量化再换空间。  
> 压测分两层：先用带 filter 标签的评测集画 Recall–Latency 曲线定工作点，再用生产 trace 分层压 QPS、叠写入看尾延迟；指标要同时钉召回、P95 和目标 QPS。

## 第 2 题归档（2026-08-22）

### 先分清三条能力：约束强度不同

「结构化输出」常被混谈，其实是三层，**可解析保证从弱到强**：


| 手段 | 模型侧做什么 | 你拿到什么 | 可解析保证 |
| --- | --- | --- | --- |
| **JSON Schema（提示 + 校验）** | Prompt 里描述 schema，或 API 的 `response_format`/`json_schema`（视供应商） | 一段声称是 JSON 的文本 | **弱～中**：格式仍可能漂；语义字段对不对另一回事 |
| **Function / Tool Calling** | 选 tool + 填 `arguments`；协议层常强制「调工具」形态 | 结构化参数对象（仍可能缺字段、类型错） | **中**：形状更稳，但仍要本地 schema 再验 |
| **Constrained Decoding**（文法/JSON Schema 进解码） | 非法 token 直接禁掉 | 语法合法的 JSON / 符合 CFG 的串 | **强（语法）**：几乎必能 parse；**不保证**业务正确、必填业务语义 |

一句话：**Constrained Decoding 买的是「一定能 parse」；Tool Calling 买的是「协议稳定」；Schema 提示买的是「便宜与通用」。三者都不等于字段业务正确。**



### 怎么保证可解析（工程默认栈）

目标拆成两层门禁：

1. **语法可解析**：能 `JSON.parse` / 能进类型对象。
2. **契约可接受**：过 JSON Schema / Zod，且过业务规则（枚举、金额范围、外键存在）。

推荐默认链路：

```text
唯一真源 schema（Zod/JSON Schema）
  → 生成：优先 tool_call 或 provider json_schema / 约束解码
  → 解析：严格 JSON（禁 markdown 围栏则先剥）
  → 校验：schema + 业务规则
  → 失败：分类 → 修复 / 重试 / 降级
  → 成功：才进写库 / 调副作用 API
```

#### 设计要点

| 点 | 做法 | 为何 |
| --- | --- | --- |
| **单一真源** | TS Zod（或同类）生成 JSON Schema；Prompt、校验、OpenAPI 同源 | 防「提示里的字段」和「代码里的字段」漂移 |
| **Schema 宜窄** | `additionalProperties: false`；枚举写死；少 `any`；深层对象拆平或限深 | 模型更容易填对；约束解码状态机也更小 |
| **禁止散文包裹** | 要求「只输出 JSON」或只用 tool_arguments；解析前剥 ` ```json ` | 最常见失败源是 markdown 围栏和尾注 |
| **流式策略** | 半截 JSON 不落库：增量缓冲到闭合，或自然语言流式 + 末枪非流式刷结构 | 见基础篇流式题；结构化路径优先完整对象 |
| **副作用后置** | 校验通过前不执行退款/发信/写主库 | 解析成功≠业务可执行 |
| **可观测** | 记 `schema_version`、失败阶段（parse / validate / business）、原始截断哈希 | 才能调参和做评测门禁 |

供应商能力怎么选（面试叙事）：

- 有 **constrained / strict json_schema**：语法层优先用它，本地仍做业务校验。
- 只有 tool calling：把「业务输出」也建成一个虚拟 tool（如 `submit_result`），比「聊天里吐 JSON」稳。
- 都没有：Prompt + 低温 + 少字段 + 强校验 + 短重试；接受更高失败率与成本。



### 解析失败：先分类，再选动作

不要一失败就「再调一次大模型」。按失败类型分支：


| 失败类型 | 信号 | 优先动作 |
| --- | --- | --- |
| **壳损坏** | 截断、非 JSON、多余文本 | 剥围栏 / 括号补全启发式；不行再短重试 |
| **schema 不合** | 缺字段、类型错、枚举外 | 把校验错误列表塞回模型「只修 JSON」；或降字段集 |
| **业务规则不过** | 金额超限、ID 不存在 | **别让模型瞎改 ID**；查库补全或澄清用户；规则失败常直接拒 |
| **工具选错 / 多工具** | 调了不该调的、arguments 张冠李戴 | 重试时收紧 allowed tools；或规则路由掉模型自选 |
| **模型拒答 / 安全** | 空、refusal | 换话术或人工；勿无限重试烧钱 |

#### 重试（Retry）

- **预算**：次数硬顶（如 2）、总 token / 延迟预算、幂等键；超过 → 降级，不空转。
- **何时重试**：瞬时截断、明显格式漂、供应商 5xx；同一校验错误连续两次相同 → 停，换策略。
- **怎么重试**：降温、缩短 schema、改用 tool_call / 约束解码、只回传「错误路径 + 期望类型」而非整段聊天重跑。
- **不要**：提高 temperature「赌一次」；对已有副作用的调用无幂等重放。

#### 修复（Repair）

分层，成本从低到高：

1. **确定性修复**：剥 markdown、去尾逗号、提取首个 `{...}`、UTF BOM；能本地修好就不调用模型。
2. **Schema-guided 修复**：小模型 / 同模型 + 「这是校验错误，只输出合法 JSON」；输入 = 坏串 + error list，**禁止改用户原意字段以外的内容**（可要求 `patch` 或整对象二选一，整对象要 diff 审计）。
3. **字段级回填**：仅缺省可选字段时填默认；必填缺失则追问或降级，不捏造。

风险：修复模型可能「编造」缺失业务字段——**高风险字段（金额、账号、权限）禁止自动修复填值**，只能拒或问人。

#### 降级（Fallback）

按产品可接受度选，并写进 SLA：

| 级别 | 行为 | 适用 |
| --- | --- | --- |
| **收窄契约** | 少字段、扁平 JSON、枚举更粗 | schema 过复杂导致稳定失败 |
| **换通道** | Prompt JSON → Tool Calling → 约束解码；或换更强/更稳模型 | 某一供应商格式不稳 |
| **交互降级** | 改成多轮表单 / 选项点击，模型只做分类 | 抽槽反复失败 |
| **人工 / 队列** | 进审、工单；返回「暂不可自动处理」 | 资金、合规、不可逆动作 |
| **安全拒答** | 明确失败码给上游，不返回半结构化糊弄 | 下游会盲信 JSON 时必须 |

一句话：**重试买偶然；修复买格式；降级买可用性；业务硬约束从不靠模型「修到过」。**



### 和评测、成本的衔接

- 离线门禁：**Schema 通过率**、字段准确率、修复后仍错率、平均重试次数、P95 延迟含重试。
- 成本：每次失败重试计入会话成本墙；监控「修复调用占比」，突增说明 schema 或模型回归。
- 版本：`schema_version` 与 Prompt/模型一起钉；破坏性改字段 = major，解析代码同发。

### 面试口述（约 45 秒）

> 可解析我分两层：语法能 parse，契约能过 schema 和业务规则。优先用 tool calling 或约束解码把语法钉死，本地 Zod/JSON Schema 做唯一真源再验业务。  
> 失败先分类：壳坏就确定性剥离或短重试；schema 错就带错误列表修 JSON；业务规则错往往拒或查库，不让模型改金额和 ID。重试有次数和预算顶，高风险字段禁止自动填值。  
> 再不行就收窄 schema、换通道、改成表单或转人工，并给上游明确失败码，绝不把半截对象当成功。

## 第 3 题归档（2026-08-22）

### 路由是策略引擎，不是「再调一个大模型选模型」

多模型路由 = 在 **SLA × 预算 × 安全边界** 下，为每条请求选一条执行路径（模型 + 工具集 + 是否 RAG/Agent）。  
它解决的是「所有流量打最贵最慢模型」不可持续，以及「全打小模型」质量塌。

一句话：**先定档位与硬约束，再用便宜分类器贴标签；路由决策必须比主模型快一个数量级，否则分类器自己就是瓶颈。**



### 四维怎么分流（先规则，后模型）

不要把难度、成本、延迟、安全揉成一个 softmax。拆成 **硬闸 + 软偏好**：


| 维 | 典型信号 | 硬闸（不让分类器否决） | 软偏好（分类器/分数可调） |
| --- | --- | --- | --- |
| **安全** | 租户等级、PII、未成年人、工具副作用、越权话术 | 敏感走私有/隔离区；禁止工具的路径；高危必须 HITL | 普通内容可走云 API |
| **成本** | 会话已耗 $/token、租户套餐、是否写操作 | 触顶 → 只允许小模型或拒新 Agent 步 | 简单问答走小模型 |
| **延迟** | 产品线 SLA（客服 vs 批处理）、是否流式 | P95 墙：超时换快模型/截断 | 闲聊走快模型 |
| **难度** | 多跳、长上下文、代码、数学、要工具 | 无；难度是估计 | 难例升级、易例短路 |

推荐决策顺序（面试好记）：

```text
安全档（必须）→ 成本/配额墙 → 延迟档 → 难度/任务类型 → 选具体模型与是否开工具
```

安全永远最先：分类器可以把「闲聊」判成 easy，但不能把「退款」判成无工具小模型。

常见档位（按产品裁）：

| 档 | 谁去 | 例子 |
| --- | --- | --- |
| **L0 规则/检索** | 不调生成模型 | FAQ 精确命中、订单号直查 |
| **L1 小/快** | 分类、改写、短答、抽槽 | 意图、标题、简单客服 |
| **L2 主模型** | 默认生成 + 轻量工具 | 多数问答 |
| **L3 强模型 / Agent** | 难例、多步、代码、对质 | 升级、投机失败后的重跑 |
| **L-sec 隔离** | 私有化/脱敏后的模型 | 证件、薪资、未公开数据 |

「投机解码 / speculative routing」：L1 先出，校验（schema、检索忠实、规则）不过再 L3——用平均成本换尾部质量，但要算清双倍调用的预算。



### 入口分类器怎么配

分类器只输出 **标签/分数**，不直接调用下游模型。输入尽量短：本轮用户话 + 少量会话摘要 + 租户/安全元数据，**不要把整段 RAG 塞进分类器**。

| 分类器形态 | 延迟/成本 | 适用 | 坑 |
| --- | --- | --- | --- |
| **纯规则** | 亚毫秒 | 正则/关键词、有订单号、明确「退款」、租户旗标 | 覆盖窄；要版本化 |
| **轻量分类模型**（本地小模型 / 专用 classifier） | 几 ms～几十 ms | 意图、难度粗档、是否需要工具 | 要评测集；漂移要重训 |
| **嵌入 + 近邻/阈值** | 一次小 embedding | 已知意图簇 | 新意图会糊 |
| **用主模型自路由** | 一次完整预填 | 几乎不该当默认 | **路由成本 ≈ 一次问答**，必成瓶颈 |

输出建议结构化且窄：

```text
safety_tier: public | pii | restricted
task: faq | qa | extract | agent | refuse
difficulty: 1–3
need_tools: bool
latency_class: interactive | batch
```

然后 **查表** 得到 `model_id + tool_allowlist + max_steps`，而不是让分类器吐模型名（模型名会变，表好换）。

校准：

- 离线：golden（应走 L0/L1/L3/拒答）上的精确率/召回；**高危漏分到低档 = 事故**，宁可 over-route 到安全档。
- 在线：各档流量占比、升级率、错档人工抽检；难度分类器宁可将「不确定」送 L2，不要把退款送 L1。
- 安全标签与业务标签分开模型或分开规则，避免一个 softmax 里安全被难度稀释。



### 回退策略怎么配

回退 ≠ 无脑换更大模型。按失败类型选方向（升、平、降）：


| 触发 | 方向 | 动作 |
| --- | --- | --- |
| **供应商 429/5xx/超时** | 平级或降延迟 | 换同档备用供应商；或降到更快模型并标记 `degraded` |
| **质量门禁失败**（schema、忠实度、拒答不当） | 升级一次 | L1→L2 或 L2→L3；次数硬顶 1 | 
| **安全命中** | 不升级能力 | 换隔离模型或拒；禁止「更强模型绕过护栏」 |
| **配额触顶** | 降档 | 关 Agent、关大模型、只检索摘要 |
| **分类器超时/失败** | 安全默认 | 走 **默认档**（通常 L2 + 全护栏），不要卡住整请求 |
| **用户显式要深度** | 允许升级 | 仍受安全/成本墙约束 |

预算：每请求 `max_upgrades = 1`、总模型调用次数顶、总 $ 顶；升级要带原因码进 trace。  
幂等：回退重跑前若已执行副作用工具，禁止换模型再跑同一写操作。

和基础篇「降级」对齐：降级是保活（有答案但可能变弱）；升级是保质（多花钱）。两者都要有顶，并在 UI 上可区分「完整 / 降级」。



### 如何避免路由本身成为瓶颈

路由的 SLA 应写成：**分类 P95 ≪ 主模型 TTFT**（例如分类 < 20–50ms，而交互 TTFT 目标 300ms+）。

| 手段 | 做法 |
| --- | --- |
| **默认短路** | 多数流量规则命中 L0/L1 直接走，不调分类模型 |
| **分类器要「笨而快」** | 本地小模型 / 规则；禁大模型自路由当热路径 |
| **短输入** | 只分类本轮 + 标签；长文档不进路由器 |
| **缓存路由决策** | 同会话、同意图指纹短 TTL；system 稳定时可缓存「闲聊→L1」 |
| **异步不挡首包** | 需要时：先按默认档流式，分类结果晚到只影响是否升级（或仅用于下一轮）——交互产品可接受「先弱后强」要产品拍板 |
| **水平扩** | 分类器无状态、可复制；不要中心化「再问一次 GPT 选模型」 |
| **失败开放** | 分类器挂了走默认档 + 告警，不要让网关排队等分类 |
| **观测** | 单独打 `router_ms`、档位分布、升级率；router_ms 占比 E2E 超阈值就简化规则 |

反模式（面试主动提）：

- 用 70B 做入口分类；
- 分类器输入 = 全历史 + 全 RAG；
- 每个请求串行：分类大模型 → 再生成；
- 路由服务同步调外部 LLM 且无超时默认档。

### 评测与发布

- 离线：同一评测集跑「全 L3」作质量上界、「全 L1」作成本下界、再跑路由策略，看 **质量掉多少、成本/延迟省多少**。
- 护栏：高危任务错分到无工具档的率必须 ≈ 0。
- 发布：路由表与分类器版本进 policy；A/B 的是整条路由策略，不只换一个模型名。

### 面试口述（约 50 秒）

> 路由我按硬闸再软偏好：安全档和配额墙先拍死，再按延迟和难度选 L0 规则、L1 小模型、L2 主模型、L3 强模型/Agent。分类器只打窄标签，查表映射到模型，不让它直接吐模型名。  
> 分类器必须是规则或本地小模型，输入要短，P95 远小于主模型 TTFT；挂了走带护栏的默认档，绝不热路径上再调一次大模型选模型。  
> 回退按原因：可用性问题平级切供应商或降速；质量门禁失败只允许升级一次；安全命中只换隔离或拒绝，禁止用更强模型绕过。每次决策和升级原因进 trace，用「相对全走大模型省多少成本、质量掉多少」做门禁。

## 第 4 题归档（2026-08-22）

### 先分清三种「缓存」，别把语义缓存当银弹

| 类型 | 命中条件 | 缓存什么 | 正确性风险 |
| --- | --- | --- | --- |
| **精确缓存** | 规范化后的 query / 请求指纹完全一致 | 完整响应或中间结果 | 低（仍要 TTL / 版本） |
| **Prompt Cache**（供应商前缀缓存） | 同一长前缀重复预填 | 不算「答案复用」，只省预填 | 几乎无业务语义风险 |
| **语义缓存** | embedding 近邻超过阈值 | **别人的答案**当这次的答案 | **高**：近 ≠ 同； prime 冲突点 |

语义缓存 = 用向量近邻把「问得像」的历史回答直接返回，换延迟和 token。  
一句话：**只缓存「答案不随外界状态变、且近邻几乎同义」的读请求；写操作、强时效、多租户串线，默认禁止。**



### 适合什么场景

适合（命中值得、错命中代价低）：

- **稳态知识**：产品 FAQ、帮助文档、政策解释（文档版本钉在 cache key 里）。
- **同义改写密集**：客服里同一问题换说法占比高，精确缓存打不中。
- **只读、无副作用**：不调写工具、不依赖「此刻库存/余额/工单状态」。
- **可接受轻微过时**：命中时 UI 标明「来自缓存 / 可能不是最新」，或短 TTL。
- **成本墙紧、QPS 高**：重复问占流量大头，缓存 P95 远小于一次 LLM。

不适合 / 默认关闭：

- 订单、价格、库存、权限、医疗剂量等 **事实随库变**。
- Agent 写操作、退款、发信——缓存的是「上次成功剧本」会误执行。
- 个性化强（「我的」合同、薪资）却 **key 不带 user/tenant**。
- 问句差一个否定词/主体（「能退」vs「不能退」、「A 产品」vs「B 产品」）——近邻最容易阴沟翻船。
- 多轮指代（「那这个呢」）——嵌入的是残缺问句，必须把解析后的指代补全再检索，否则乱命中。

和路由的关系：语义缓存挂在 **L0/L1 之前或并列**；命中则跳过模型。安全档 `restricted`、`need_tools=true`、会话已有未提交副作用 → **强制 miss**。



### 相似度阈值怎么定

阈值不是调一个 cosine 魔法数，而是 **错命中 vs 漏命中的代价不对称**。

| 原则 | 做法 |
| --- | --- |
| **宁漏勿错** | 业务答错成本高 → 阈值从严（更高相似度才命中）；FAQ 可稍松 |
| **不要裸阈值** | 同时看：top1 分、top1−top2 间隔（margin）、是否同一 `intent`/`doc_version` |
| **分场景阈值** | FAQ 一套、技术问答一套；否定词/实体冲突则否决命中 |
| **校准数据** | 用「应命中 / 不应命中」对；画 PR 曲线，盯 **错命中率**（false hit），不是只盯命中率 |
| **embedding 钉版本** | 换嵌入模型 = 全量失效重建；分数不可跨模型比 |

辅助硬规则（比微调 0.01 更管用）：

1. **实体约束**：抽到的产品名、订单号、人名必须一致，否则 miss。
2. **否定/情态**：源问与缓存问的否定极性不一致 → miss。
3. **语言/渠道**：中英、内部/对外话术可分桶，避免串答案风格。
4. **只接受 top1 且 margin 足够**：两个近邻分数接近说明歧义，走模型。

上线节奏：先精确缓存 → 再小流量语义缓存（高阈值）→ 看错命中抽检再降阈值。不要一上来全站 0.8 一刀切。



### 失效策略（比阈值更容易救正确性）

Cache key / 记录上必须带 **隔离与版本**，不能只有向量：

```text
tenant_id + user_scope(optional) + intent_bucket
+ prompt_id@version + model_id + rag_index@version
+ tool_policy_hash + 安全档
```

| 失效手段 | 何时用 | 说明 |
| --- | --- | --- |
| **TTL** | 默认都要 | 即使「知识稳定」也给小时～天级；强时效用分钟级或不开 |
| **版本驱逐** | Prompt / 索引 / 模型 / 政策发版 | 发版把对应 `version` 的 key 批量删或命名空间切换 |
| **源文档失效** | RAG 某 doc 更新 | 记录写入时存 `source_ids`；文档变更按 tag 删 |
| **主动禁写** | 事故、错误答案被踩 | 运营打 `ban`；点踩/转人工回流为负例，降低该簇命中 |
| **租户驱逐** | 租户知识库更新、权限变更 | 只清该 tenant，禁止全局模糊扫 |
| **不缓存** | 工具结果含实时字段 | 可缓存「话术骨架」，实时槽位每次重填——或直接不缓存 |

写入策略：只缓存 **校验通过** 的回答（schema、护栏、非拒答、非降级糊弄）；流式结束后再写；用户点踩不写或立即删。

多租户：向量检索必须带 **metadata filter（tenant）**，与进阶第 1 题同一坑——post-filter 小 top_k 会串或空；错租户命中是事故不是「阈值再高一点」。



### 与业务正确性冲突时怎么处理

冲突本质：**近邻相似是语言相似，不是命题等价。** 处理优先级从硬到软：

1. **范围闸**：任务类型白名单（FAQ/稳态知识）；写路径、实时查询、高危安全档不进缓存。
2. **等价闸**：实体/否定/数字（价格、日期、版本号）不一致则 miss——数字尤其不能靠向量。
3. **新鲜度闸**：命中响应带 `cached_at`；超 SLA 或源版本落后则 miss。
4. **诚实 UI**：标注「缓存回答」；提供「重新生成」。不要把缓存答封装成实时查询结果。
5. **错命中熔断**：某簇点踩率/纠错率升高 → 自动提高阈值或关该 intent 的语义缓存，退回精确缓存或模型。
6. **评测门禁**：上线看 **错命中率、缓存答案与现网 gold 的一致率、投诉/转人工**；命中率高但 CSAT 掉 = 立刻收阈值。

和「正确性」对账的面试句：**缓存优化的是重复劳动，不优化真值；真值仍以库、索引版本、工具返回为准。** 语义缓存只允许代替「同一问题上一次已验证的生成」，不允许代替一次 `SELECT`。

### 压测与观测

- 指标：命中率、**错命中率**（抽检/对标注）、P95（命中 vs miss）、$/请求下降、版本驱逐后的 miss 尖峰。
- 延迟：embedding + ANN 必须远小于一次 LLM；否则语义缓存自己成瓶颈（同第 3 题分类器）。
- 对照实验：精确缓存 vs 语义缓存 vs 无缓存，在同评测集上比质量和成本。

### 面试口述（约 45 秒）

> 语义缓存只适合稳态、只读、同义改写多的问题，比如 FAQ；订单价格、写工具、强个性化默认不开。阈值宁漏勿错，不能只看 cosine，还要实体和否定一致、top1 间隔够大，embedding 换版本就整库失效。  
> 失效靠 TTL 加 prompt/索引/模型版本和租户隔离，文档更新按 source 驱逐；只写入校验通过的答案。  
> 和正确性冲突时，缓存绝不代替查库：白名单任务、数字与实体硬校验、UI 标明缓存并可重新生成，错命中升高就熔断该意图。命中率不是成功指标，错命中率和业务投诉才是。

## 第 5 题归档（2026-08-22）

### 原则：租户身份是控制面事实，不是模型填的字段

多租户 AI SaaS 的隔离 = **每个请求上的 `tenant_id` 由鉴权注入**，再贯穿数据、索引、配额、密钥、Prompt/工具策略。  
模型输出、Tool 参数、用户上传文档里的「我是管理员 / 查全部租户」一律无效。

和基础篇接业务同一句：**LLM 提议，鉴权层批准。** 服务账号没有跨租户上帝权。

一句话：**共享计算可以，共享可见性不行；定制知识/模型用命名空间隔离，不要靠 Prompt 说「别看别人的」。**



### 五层怎么隔离

先选隔离强度，再落产品。面试用「按合规与密度选型」，不要只押「每租户一套集群」。


| 强度 | 形态 | 何时 |
| --- | --- | --- |
| **逻辑隔离** | 共享集群 + 每条记录 `tenant_id` + 强制 filter | 默认；租户多、数据中敏 |
| **命名空间隔离** | 每租户独立 collection / bucket / schema | 检索过滤复杂、或客户要数据面隔离证明 |
| **专用实例** | 独立 VPC/集群/密钥 | 强合规、大客户、噪声邻居不可接受 |

无论哪档，**应用层 ACL 都必须在**。专用实例不是借口去掉 `tenant_id` 校验。

#### 1. 数据

| 面 | 做法 |
| --- | --- |
| **OLTP / 对象存储** | 行级 `tenant_id`；对象 key 前缀 `/{tenant}/`；查询 API 强制注入，禁止模型拼 WHERE |
| **会话 / 记忆** | key = `tenant + user + session`；长期记忆写入带作用域（见基础篇记忆题） |
| **日志 / trace / 评测集** | 默认按租户分区；支持导出与删除（退出/GDPR）；禁止把 A 的 prompt 原文送进 B 的评测 |
| **出站** | 调供应商时剥离他租数据；网关按租户做 DLP 规则可不同 |

#### 2. 索引（向量 / 倒排）

与第 1 题同一硬坑：**检索必须 pre-filter 或独立索引**；post-filter + 小 top_k 会串租或空结果。

| 方案 | 隔离 | 代价 |
| --- | --- | --- |
| **共享 index + 强制 `tenant_id` filter** | 逻辑 | 省碎片；过滤实现必须正确；压测要带租户选择性 |
| **每租户 collection** | 更强 | 小租户索引碎片、冷启动、运维多 |
| **平台公共知识 + 租户私库两路** | 公共库无租户秘密；融合时私库优先、公共库不得含客户数据 | 要防「公共库被租户文档污染」 |

写入：embedding 任务队列按租户鉴权；文档解析 worker 不可用「全局扫描目录」。删除/更新租户库不得动其他 namespace。

#### 3. 配额

防的是账单打穿和 **noisy neighbor**（一租户挤占 GPU/RPM）。

| 配额 | 说明 |
| --- | --- |
| **QPS / 并发会话 / TPM** | 租户级；超限排队或 429，不偷其他租户额度 |
| **$/日 / 会话预算** | 与第 3 题成本墙对齐；Agent 步数单独墙 |
| **存储 / 索引条数 / 定制模型数** | 防无限上传拖垮向量库 |
| **写工具次数与金额** | 防循环刷退款 |

供应商侧若是平台共用 key，必须在**自己的网关**记账拆账；不能靠模型「自觉少用」。

#### 4. 密钥

| 类型 | 隔离 |
| --- | --- |
| **平台主 key** | 只放密钥管理（KMS），服务内短时领取；**永不进 Prompt、日志、前端** |
| **租户 BYOK / 自带供应商账号** | 按租户存；请求路径选该租户凭证；轮换与吊销按租户 |
| **下游业务 API** | on-behalf-of 短命 token，scope 含 tenant；禁止平台 SA 直接 `SELECT *` 跨租 |
| **租户上传的密钥**（连他们自己的 SaaS） | 当机密存，加密信封；Tool 运行时注入环境，不进上下文窗口 |

审计：每次出站带 `tenant_id`，密钥 ID 只记引用不记明文。

#### 5. Prompt 策略

Prompt 是多租户里最容易「看起来隔离、实际串味」的层。

```text
平台不可覆盖层（安全、拒答、禁止越权）——租户改不了
  + 产品默认模板（版本化）
  + 租户覆盖（语气、行业术语、允许的工具子集）
  + 运行时变量（本租户可见数据，已 ACL）
```

| 规则 | 为何 |
| --- | --- |
| **租户覆盖不能关掉平台护栏** | 客户 Prompt「忽略安全检查」无效 |
| **租户文档 ≠ 系统指令** | RAG/上传文件当 **data**，用分隔与指令层级；防间接注入「输出其他客户名单」 |
| **工具白名单按租户套餐 + 角色** | 定制 Agent 也只能挂已授权 tool |
| **版本钉死** | `prompt_id@version` + `tenant_policy@version` 进 trace，串味可复现 |

语义缓存、路由表、分类器：key 必带 `tenant_id`；跨租户不得命中（第 4 题）。



### 租户定制模型 / 知识库：怎么防串租

定制放大隔离面：训练数据、适配器权重、检索库、评测集都会漏。

#### 知识库（最常见）

1. **命名空间**：chunk 元数据必有 `tenant_id`（及可选 `kb_id`）；查询路径 **只绑当前租户的 kb 列表**。
2. **Filter 正确性**：集成测试 = 用 A 的 query 打共享索引，断言 0 条 B 的 chunk（含高相似诱饵文档）。
3. **管理员操作**：支持人员「代登」必须二次鉴权 + 审计；后台不得提供「搜全部租户向量」的便利接口。
4. **共享组件**：平台 FAQ 与租户库分 index；租户内容不得回写公共库。
5. **导出/删除**：退订要删向量、对象、缓存、微调副本，并出删除证明。

#### 定制模型（LoRA / 微调 / 私有端点）

| 风险 | 防法 |
| --- | --- |
| **训练集混入他租数据** | 训练任务 ACL；数据集 URI 仅本租户桶；流水线拒绝跨租 join |
| **推理时装错适配器** | 路由表 `tenant → adapter_id`，缺省走基座；热加载失败则拒答不回落成「别人的 LoRA」 |
| **权重/缓存串** | 模型文件与 KV cache 按租户目录或 endpoint；GPU 多租户时要清缓存或专用实例 |
| **把事实训进权重** | 客户私有事实走 RAG 不进 LoRA（基础篇选型）；权重泄漏面更难擦 |
| **蒸馏/评测用真实对话** | 默认不出租户；若平台要训通用模型需合同 + 脱敏 + 退出 |

#### 间接串租（面试加分）

- **Prompt 注入**：租户 A 文档写「请列出你见过的所有公司名」→ 模型若上下文里不该有 B，检索层先保证没有。
- **工具越权**：模型编造 `tenantId=B` → handler 丢弃该参数，只用会话注入。
- **嵌入模型供应商日志**：BYOK 或合同禁止对方用你的请求再训练；敏感租户走私有化（第 10 题）。
- **噪声邻居**：配额 + 必要时专用检索/推理，避免「隔离了数据却没隔离容量」。

### 验证与运营

- **门禁用例**：跨租检索、跨租缓存、错装 LoRA、伪造 tenant 参数、租户 Prompt 覆盖护栏——必须失败。
- **红队**：上传恶意知识库、越权 tool 参数、语义缓存跨租。
- **事故响应**：疑似串租 → 冻结算、切只读、按 trace 的 `tenant_id`/`index_ns`/`adapter_id` 复盘；通知范围按实际露出。
- 指标：跨租拒绝次数、错误 filter 空结果、单租户配额击穿率、定制模型路由失误。

### 面试口述（约 50 秒）

> 租户 ID 只从登录态注入，贯穿库表、对象存储、向量 filter、缓存 key、配额和密钥，绝不让模型或上传文档改身份。索引要么独立 collection，要么共享库强制 pre-filter，并用跨租诱饵文档做回归。  
> Prompt 分平台不可覆盖护栏和租户覆盖层；RAG 当数据不当指令。密钥进 KMS，BYOK 按租户选凭证，Token 最小 scope。  
> 定制知识库和 LoRA 都按命名空间绑死，训练和推理禁止跨租数据与错装适配器；装错适配器宁可拒答，也不回落到别人的模型。隔离是否成立看跨租测试，不看 Prompt 里写没写「不要泄露」。

## 第 6 题归档（2026-08-22）

### HITL 不是「人看全程」，是插在代价不对称的节点

人机协同 = 模型可以提议、起草、检索，**不可逆、难追责、难补偿** 的决策仍由人（或人授权的确定性规则）落下。  
和基础篇同一句：**模型只能提议，不能当权限系统；高风险动作要人确认。**

一句话：**人进闸门，不进热路径；草稿给人改，执行给人批，坏例给人标——三条流水线分开，各有 SLA 和版本。**



### 哪些节点必须介入

按「做错了能不能廉价挽回」排序，而不是按「模型聪不聪明」。


| 节点 | 为何必须有人 | 典型形态 |
| --- | --- | --- |
| **对外不可逆写** | 退款、转账、改价、删数据、发正式函/客邮、法律承诺 | 审批队列；模型只生成 payload |
| **安全与合规灰区** | 自伤、未成年人、医疗剂量、歧视、越权索取 | 升级人工 / 安全岗；禁止自动放行 |
| **无依据仍要下结论** | RAG 空、工具失败、低置信 | 转人工或拒答，不让模型赌 |
| **高影响记忆/画像写入** | 「过敏」「法定名」「额度」写错会长期害人 | 用户确认或业务系统回写，不单靠抽取 |
| **策略发版** | Prompt、路由表、护栏词表、索引切换 | 人工签核 + 离线门禁（基础篇评估题） |
| **串租/泄密疑似** | 第 5 题事故面 | 冻路径 + 安全人工，不自动「修一下再发」 |

可以不闸（或抽检即可）：只读查询、有引用的 FAQ、已确认模板的重发、用户显式点选的低风险填表。

和路由的衔接（第 3 题）：`safety_tier=restricted` 或 `need_tools` 且工具为写 → **强制 HITL 或二次确认**，分类器不能把退款判成全自动。

产品上三档即可面试说清：

```text
自动执行（只读/低风险）
  → 人审草稿后执行（对外表达、中风险写）
    → 双人/权限岗审批后执行（资金、合规、不可逆）
```



### 三条可运营流水线

运营 = **工单状态机 + 角色 + SLA + 审计 + 回流**，不是聊天里说「请人工看一下」。

#### 1. 草稿确认（Draft）

适用：客服回复、合同摘要、对外邮件、工单备注——**发出去才有后果**。

| 要素 | 做法 |
| --- | --- |
| **产物** | 结构化草稿：正文 + 引用/依据 + 建议动作（尚未执行） |
| **人做什么** | 改字 / 一键通过 / 驳回重生成；默认不让人从零写 |
| **超时** | 交互态：等人；异步：SLA（如 15min）超时升级或降级为「未发送」 |
| **身份** | 确认者 = 会话所属坐席或用户自己；模型说「用户已同意」不算 |
| **审计** | 存 `draft_id`、原文、改定稿、确认者、policy 版本 |

要点：流式可以给坐席看草稿，**发送按钮在人**；自动发送仅限白名单模板 + 已通过的槽位。

#### 2. 高风险动作审批（Approve）

适用：tool 已填参、校验已过 schema，**差最后一跳副作用**。

```text
模型提议 tool_call
  → 服务端鉴权 + 业务规则（金额墙、资源归属）
  → 入审批单（只读展示参数，人不可被诱导改到他租资源）
  → 通过则用同一幂等键执行；驳回则回灌原因，不执行
```

| 要素 | 做法 |
| --- | --- |
| **队列** | 按风险/金额分级；资金类独立队列与权限 |
| **人不可越权改参** | 可驳回或改金额到规则内；`tenant_id`/`user_id` 锁死 |
| **防疲劳** | 批量勾选要二次确认；高危禁止「全选通过」 |
| **超时与挂起** | 超时不默认执行（fail-closed）；用户侧展示「审批中」 |
| **与工作流** | 能接既有 BPM 就接；AI 不自建一套无法审计的「群里点头」 |

和基础篇接业务一致：真正同意/驳回仍走工作流按钮或审批 API，Agent 不得空转死等——提交 `approval_id` 后结束本轮或订阅回调。

#### 3. 坏 case 标注回流（Label → Eval）

适用：点踩、转人工、审批驳回、安全拦截、坐席大改草稿——**这是质量系统的矿，不是客服边角料**。

```text
在线信号（点踩 / 转人工 / 驳回 / 大改）
  → 采样入队列（分层：安全全量，其余按比例）
  → 标注（rubric + 错误标签：幻觉/漏检/越权/错槽…）
  → 入库 golden / 回归集（钉 policy 版本与脱敏）
  → 改 Prompt / 检索 / 路由 / 护栏
  → 离线套跑不过不发版
```

| 要素 | 做法 |
| --- | --- |
| **标签体系** | 固定枚举，能指导改哪一层（检索 vs 生成 vs 工具 vs 政策） |
| **谁标** | 安全/事实用业务专家；语气可培训众包；双人盲评算一致率 |
| **去标识** | 租户数据进评测集要脱敏与合同（第 5 题） |
| **节奏** | 日常每周 N 条；发版加严切片；同一坏例修复后应变成回归必过 |
| **闭环指标** | 重复错误率下降、转人工率、审批驳回率、坐席编辑率 |

人工贵，所以目标与基础篇第 4 题相同：**缩小必须人标的比例，不取消人**——LLM-judge 用人工分校准后进 CI，人转向新模式和安全一票否决。



### 做成「可运营」还要什么

缺了这些就只是功能，不是流程：

1. **角色**：坐席（改草稿）、主管（批高危）、质检（标坏例）、工程（把标签变成评测）。互不替代。
2. **SLA 与容量**：按到达率配人；高峰走排队而不是偷偷改成全自动。
3. **状态机**：`drafted / pending_approval / approved / rejected / executed / labeled`，每步可查询。
4. **默认 fail-closed**：审批超时、标注积压，不自动当通过。
5. **观测**：HITL 介入率、等待时长、通过/驳回/编辑率；介入率暴跌要查是不是闸被旁路。
6. **版本**：人批的是哪版 Prompt/工具 schema，回放才有意义。

反模式：把 HITL 做成「模型自己问自己是否确认」；审批群里截图无单号；坏例进表格不进 eval 仓库；为降转人工而放开退款自动过。

### 面试口述（约 50 秒）

> 人只卡代价不对称的点：对外不可逆写、合规灰区、没依据还要下结论、高影响记忆、策略发版。只读和有引用的 FAQ 可以自动。  
> 运营上拆三条队列：草稿确认是人改或点发送；高风险是鉴权过后再入审批单，fail-closed、参数锁身份、接既有工作流；坏 case 从点踩转人工驳回采样，按错误层打标进 golden，改策略必须离线回归。  
> 角色、SLA、状态机和审计要齐，超时默认不执行。HITL 成功不看「人看了多少」，看重复错误和违规是否下降，以及闸有没有被旁路。

## 第 7 题归档（2026-08-22）

### 差在哪：多模态是「先变成可引用的证据」，再走原文本链路

纯文本链路默认假设：**用户话和知识都已经是可信 token**。  
图文 / 语音 / 文档解析多了一段 **感知层**：OCR、ASR、版面、切页、多模态 embedding——输出是带噪声、带坐标、可能错位的「伪文本」。

一句话：**下游 Agent 看到的不是事实，是某次解析的假设；对齐、切页、转写错误必须当一等公民进契约，不能当预处理细节。**



### 和纯文本比，工程上多出来的面


| 面 | 纯文本 | 多模态 |
| --- | --- | --- |
| **输入契约** | 字符串 | 字节 + MIME + 页码/时间轴 + 分辨率；同一文件多种派生（图、文本层、表格） |
| **延迟构成** | 检索 + LLM | 解析/转写常主导 E2E；要异步 job + 进度，忌在 Agent 循环里同步啃 PDF |
| **证据** | chunk 文本 | 必须能指回 **页/框/时间戳**，否则无法审计、无法 HITL |
| **错误形态** | 幻觉、漏检 | 再加：看错字、切错栏、表头错位、同音词、说话人糊 |
| **安全** | Prompt 注入 | 图中藏字、PDF 不可见层、语音对抗；护栏要扫 **派生文本 + 原文件策略** |
| **Token** | 字数近似 | 图按 patch/tile 计费；整本 PDF 塞进视觉模型会爆窗爆钱 |
| **评测** | 文本 golden | 还要：ASR WER、OCR 字段准确、切页边界、跨页表、指代页码 |

推荐默认架构（面试好画）：

```text
原文件/音频不可变存储
  → 解析器（版本钉死）→ 结构化中间表示（页/块/表/时间戳 + 置信度）
  → 索引（文本 + 可选多模态向量，metadata 含 locator）
  → 文本/多模态 LLM + Agent（只读中间表示，写回带 locator 的引用）
```

中间表示是真源给 Agent 用；原件留给人核对。不要让每步 Agent 直接「再看一遍 200 页图」。



### 模态对齐：让「这句话」对得上「那一处」

对齐 = 跨模态的 **同一世界锚点**，不是把图和字拼进同一个 Prompt 就算齐。

| 要对齐什么 | 做法 |
| --- | --- |
| **空间** | OCR/版面：block 带 bbox + page；引用格式 `doc_id#p12#b3` |
| **时间** | ASR：词级或句级 timestamps；引用 `audio_id#t00:12–00:18` |
| **语义** | 图注、表头、邻近标题一并进 chunk，避免「单元格数字」脱离列名 |
| **身份** | 多图多文件：每条证据带 `asset_id`，禁止「上面那张图」无解析指代 |
| **模型 internally** | 若用 VL：问的是图还是 OCR 文本要显式；混用时声明以哪路为准（钱、专名优先结构化字段） |

冲突处理（图文不一致）：

1. **结构化字段优先**（发票金额走表格/正则，不走散文 OCR）。
2. **低置信走另一路**（OCR 差则 crop 给 VL；VL 贵则只对低置信块调用）。
3. **对人暴露冲突**：「识别金额 A，图中印刷体像 B，请确认」——高风险数字进第 6 题 HITL。

检索侧：纯文本向量对扫描件会瞎；需要 OCR 后再嵌，或图文双路（第 1 题 hybrid 思想：关键词对专名/货号，向量对语义）。Filter 仍带租户与 `doc_id`。



### 长文档切页：切的是「可检索单元」，不是平均页数

PDF/扫描件的坑：双栏、页眉页脚重复、表格跨页、目录页码 ≠ 文件页码。

| 策略 | 何时 | 注意 |
| --- | --- | --- |
| **按版面块** | 有结构的报告 | 优于死切 N 字；块过大仍要二次切 |
| **按页 + overlap** | 扫描件、版面烂 | overlap 保跨页句；页眉页脚进 stoplist 或单独层 |
| **表格整表/按行** | 财务表 | 跨页表要 merge；切碎则 Agent 算错合计 |
| **章节树** | 有书签/标题 | 先目录再叶子；Agent 按需 `read_page` 工具，不一次灌全书 |

给 Agent 的用法：

- **索引粗召回**（章节/页摘要）→ **工具精读**（`get_page` / `get_table`）→ 引用必须含 locator。
- `max_pages_per_turn` 预算墙，防循环把全书读进 context。
- 切页版本进 `index_version`；重解析要重建，旧引用失效（第 4 题驱逐）。

评测：跨页问题（「表 3 合计」）、页码问答、页眉噪声是否污染检索。切页调参和向量 ANN 一样要画 **召回 vs 延迟/token**，不是只求切得细。



### ASR 误差：当成脏输入，不要当成用户原话

ASR 错一个专名/否定/数字，Agent 会选错 tool、填错槽、甚至触发写操作。

| 误差类型 | 下游伤害 | 兜法 |
| --- | --- | --- |
| **专名 / 货号** | 检索 miss、查错订单 | 热词/偏置；与账户内实体做模糊对齐；低置信强制确认 |
| **数字 / 日期** | 错金额、错预约 | 数字字段二次校验；复述确认；必要时 DTMF/键盘输入 |
| **否定 / 同音** | 极性反了 | 关键意图（取消/不退）高阈值；ASR 置信 + N-best |
| **标点 / 断句** | 槽位切错 | 用 N-best 或多假设给理解模型，不单信 1-best |
| **说话人 / 重叠** | 张冠李戴 | diarization；指令只认当前用户声纹/会话绑定 |
| **领域外口音** | WER 高 | 降级：转人工、改打字、或只做 FAQ 不走 Agent 写 |

Agent 侧契约：

1. **置信度进上下文**：`transcript + alternatives + word_confidence`，Prompt 要求对低置信槽 **澄清而不是调用写工具**。
2. **槽位门禁**：订单号/金额/电话与正则或查库不一致 → 不执行，走草稿确认（第 2、6 题）。
3. **幂等与复述**：执行前 TTS 复述「为订单 123 退 50 元」，人点确认。
4. **检索用多假设**：top-N 转写都去搜，融合召回，减少「听错一个字就零结果」。
5. **日志分开放**：存音频 locator + 转写版本；纠纷以音频为准，不以 ASR 文本为准。
6. **路由**：高 WER 会话降到 L1 澄清或 HITL，不要升到更强 Agent 更敢写（第 3 题：质量差应降能力不是升）。

语音链路延迟：先流式 ASR 出 partial 做意图，**写工具仍等 final + 校验**；partial 只用于「我在听」的体感。



### 和评测、护栏的衔接

- 离线：字段级 OCR/ASR 准确 + 端到端任务成功（「能否退对那一单」），分开报，避免「WER 还行但 Agent 全错」。
- 安全：解析后的文本走与用户输入同一套注入检测；不可见 PDF 层要抽出来扫。
- 成本：视觉 token 按页配额；默认「检索定位 → 小图 crop」，禁止全书转图。

### 面试口述（约 50 秒）

> 多模态和纯文本的差在感知层：OCR/ASR/切页产出的是带噪声和坐标的假设，不是真值。中间表示要带页码、框、时间戳，Agent 引用必须能指回去，原件留给人对。  
> 对齐是空间和时间锚点，图文冲突时金额专名走结构化字段，低置信才上视觉模型或问人。长文档按版面和表切，召回用摘要、精读用读页工具，跨页表要合并，还有页数预算。  
> ASR 当脏输入：热词、N-best、低置信澄清，写工具前复述确认；听不清就降级人工，不换更强 Agent。评测要拆开感知指标和任务成功率。

## 第 8 题归档（2026-08-22）

### 先分清：可枚举工作流 vs 多 Agent

基础篇判据仍成立：**步骤事先可枚举 → DAG/工作流 + Tool Call；要边看边改计划 → Agent。**  
多 Agent 是第三档：多个带不同 Prompt/工具/模型的循环，外加一个编排器。税是 **N 倍上下文、协调延迟、更难复现**。

一句话：**能用状态机串工具就不要上 Agent；能用一个 ReAct 就不要拆群聊。多 Agent 只买「异构能力、并行扇出、失败隔离、专门对质」这几样。**



### 何时比单 Agent 更合适

单 Agent 够用：同一工具箱、同一身份、计划深度用步数墙就能罩住（查单 → 答 → 偶尔再查）。

值得拆的信号（满足 2 条以上再拆）：


| 信号 | 为何单 Agent 吃力 |
| --- | --- |
| **异构策略** | 检索/写代码/合规审核要用不同模型、温度、工具白名单，塞进一个 System 会互相污染 |
| **可并行子任务** | 多文档、多源检索、互不依赖的调查；单循环只能串行烧 TTFT |
| **爆炸半径** | 写工具必须和「乱说话的调研 Agent」分开进程与权限（第 5、6 题） |
| **需要对立视角** | 高风险结论要攻击性审查，一个角色既写又审会自我辩护 |
| **上下文互挤** | 长工具日志让主循环遗忘用户目标；工人拿切片，主管只收摘要 |

不该拆：为了架构图好看；「辩论」没有评分与停止条件；工人还能互相调对方的写工具。

四种模式怎么选：

| 模式 | 拓扑 | 合适 | 不合适 |
| --- | --- | --- | --- |
| **顺序** | A 的结构化输出 → B | 流水线稳定（解析 → 抽取 → 草稿）；B 强依赖 A 的契约 | 中间要动态改计划——会变成隐形大 Agent |
| **并行** | 扇出 N 路 → 汇合 | 独立检索/翻译/多文件；要合并策略（RRF、投票、主管摘要） | 共享可变写；无汇合锁会双写 |
| **辩论** | 正方/反方 + 裁判 | 策略/合规/诊断，允许增加延迟换降低自信幻觉 | 客服热路径；没有裁判 rubric 会空转互喷 |
| **主管-工人** | Supervisor 派单、收摘要、决是否升级 HITL | 默认多 Agent 形态；工人窄工具、主管无写权或仅有「提交审批」 | 主管变成第二个全能 Agent（工具全集复制） |

和「已有工作流引擎」：审批、补尝、人工节点仍走 BPM（基础篇第 10 题）；Agent 只填单、建议下一跳，**不在群聊里冒充状态机**。



### 状态共享：默认可选披露，禁止全局可变大脑

共享过多 = 串音、越权、上下文爆；共享过少 = 工人重复劳动、结论对不上。

推荐：**黑板（Blackboard）存事实，消息传意图。**

```text
run_id
  ├── goal / 用户原话 / 身份（只读，服务端注入）
  ├── artifacts/          结构化产物（schema 版本化）
  ├── evidence/           带 locator 的引用（第 7 题）
  └── decisions/          主管决议、审批 id
工人只读自己的 inbox + 声明过的 artifact 键；禁止扫全部聊天
```

| 原则 | 做法 |
| --- | --- |
| **身份只注入** | 所有工人同一 `tenant/user`；工人 Prompt 里不许改身份 |
| **工件契约** | 工人输出走 JSON Schema（第 2 题）；主管不解析散文日记 |
| **最小可见** | 检索工人看不到退款 tool；写工人看不到他库原文，只看已批准的 payload |
| **禁止共享可变会话** | 不要把同一个 messages[] 传给所有角色追加；每人独立 thread + 引用 artifact id |
| **汇合** | 并行路写不同 key；冲突用版本号/主管合并，不用「最后写赢」 |

记忆：run 级状态 ≠ 用户长期记忆。跨 run 仍走第 5 题租户隔离的记忆服务，不把黑板当画像。



### 失败隔离：一人生病，不要全桌陪葬

隔离目标：工人挂了 → 主管拿到错误对象，决定重试/跳过/降级/HITL；**不要把失败当自然语言糊进别人上下文然后继续写库。**

| 层 | 设计 |
| --- | --- |
| **进程/权限** | 工人独立 tool 白名单；写路径单独工人 + 第 6 题审批 |
| **超时** | 每工人 wall time + 主管总预算；超时返回 `partial` 而非空转 |
| **重试** | 只对幂等读；写失败先查幂等键（基础篇接业务） |
| **取消** | 用户中断 → 取消子任务、已发出的只读可丢、已提交审批不自动撤除非产品定义 |
| **辩论** | 轮次硬顶；裁判超时 → 标 `unresolved` 升级人，不默认采纳言辞更狠的一方 |
| **降级梯子** | 多 Agent 失败 → 单 Agent 窄工具 → 单轮检索摘要 → 转人工 |

主管自己也要步数墙：防止「再派一个工人试试」死循环。同 `(worker_type, input_hash)` 连败 N 次熔断。

补偿：并行里已成功的读可弃；已成功的写走业务补偿，不靠另一个 Agent「口头撤销」。



### 可观测：一棵 trace，不要 N 段聊天记录

没有统一 `run_id` 的多 Agent 无法排障，成本也分不清是谁烧的。

| 打点 | 内容 |
| --- | --- |
| **树形 trace** | `run → supervisor_turn → worker_span`；OpenTelemetry parent-child |
| **分账** | 每节点：model、token、延迟、tool 列表；汇总 $/run |
| **状态快照** | 关键 artifact 的 hash/version，便于回放（不必把全书日志当唯一真相） |
| **决策原因** | 主管为何派谁、为何升级、为何结束——结构化枚举，方便评测 |
| **失败归因** | `worker_timeout` / `schema_fail` / `tool_403` / `budget`，不要只有「Agent 出错了」 |
| **评测** | 端到端任务成功 + 工人单元契约通过率；辩论看裁判与专家一致率 |

和路由（第 3 题）：工人可以是不同模型档；**编排器本身必须便宜**（规则或小模型），否则主管 LLM 成为瓶颈。

发布：拓扑、工人 Prompt、schema 进 `experience_id`；改「多 Agent 图」等于改产品，走评测门禁（第 9 题）。

### 面试口述（约 50 秒）

> 步骤能枚举就用工作流；一个工具箱能边看边做就单 Agent。多 Agent 只在策略异构、可并行、要隔离写权限、或需要独立审查时才拆，默认主管-工人，工人窄工具、主管不直接写库。  
> 状态用黑板放结构化产物和证据，消息只传任务；禁止共享一份可变 messages。失败按工人超时和错误对象处理，写路径幂等加审批，辩论有轮次顶，失败就降到单 Agent 或人工。  
> 观测必须是带 run_id 的 span 树和分账，主管派单原因结构化。编排器用规则或小模型，别让调度自己先烧一轮大模型。

## 第 9 题归档（2026-08-22）

### 和传统 CI/CD 差在哪：交付物是「体验组合」，不只是二进制

传统服务：代码编译 → 单测/集成 → 镜像 → 健康检查（5xx、延迟）→ 回滚镜像。  
AI 应用：同样要这些，但 **效果由 Prompt × 模型 × 索引 × 工具契约 × 护栏 共同决定**；模型非确定性，5xx 全绿也可以「礼貌地胡说」。

| 维 | 传统 | AI 应用 |
| --- | --- | --- |
| **回归对象** | 函数输入输出确定 | 还要评测集：召回、忠实、工具选择、安全红线 |
| **制品** | 一个服务包 | 多制品：app + `prompt` + `index` + `model/adapter` + `policy` |
| **版本** | git SHA / 镜像 tag | 必须有 `experience_id`（组合指纹），单回滚代码不够 |
| **发布信号** | 错误率、饱和度 | 再加：任务成功率、转人工、schema 失败、$/会话、护栏拦截 |
| **金丝雀** | 比延迟和 5xx | 还要比 **质量护栏**；流量要按会话粘滞，避免一轮对话换人格 |
| **回滚** | 上一个镜像 | **切回已知好的 experience 标签**；索引/模型可能不能瞬间重建 |
| **成本** | CI 机时 | 评测本身烧 token；门禁要分层，不能每 PR 全量 judge |
| **数据** | 测试夹具 | 评测集含生产脱敏对话，有租户与合规（第 5、6 题） |

一句话：**传统 CI 证明「还能跑」；AI CI 还要证明「还是同一类体验」。回滚的是 experience，不是只回滚一段 Prompt 或一次 kubectl。**

和基础篇对齐：离线不退步、在线不伤北极星；日志带 `experience_id` 才能把坏 case 拉回评测集。



### 流水线怎么串（推荐形状）

```text
PR
  → 契约门禁（schema / tool 选择 / 权限用例，快、确定性）
  → 小评测集（主路径 + 红线，每 PR 或合入前）
  → 构建制品（prompt 包、索引快照或 diff 任务、adapter 校验）
  → 钉 experience 候选标签（不指向生产）
  → 金丝雀 / 实验流量（会话粘滞）
  → 在线护栏 + 人工抽检（第 6 题）
  → 提升 stable 标签 或 体验回滚
Nightly / 索引重建：全量评测 + 漂移检测
```

应用代码与「话术」可以不同频发版（基础篇第 1 题），但 **合入生产的是一次 experience 提升**，不是各改各的。



### 评测集门禁：分层，别把 CI 变成无限账单

| 层 | 何时跑 | 内容 | 不过则 |
| --- | --- | --- | --- |
| **L0 契约** | 每 PR | schema 通过、禁止越权 tool、租户 filter 诱饵、结构化抽取 | **阻断合并** |
| **L1 核心集** | 合入前 | 50–200 条：主路径 + 难例 + 安全；确定性指标 + 少量 judge | 阻断或需人工签核 |
| **L2 全量 / 漂移** | nightly、索引/模型大变 | 召回、忠实、Agent 轨迹、成本/延迟回放 | 阻断提升标签，可已进主分支 |
| **L3 对抗** | 护栏/安全变更 | 注入、越权、多模态隐藏层（第 7 题） | 阻断 |

纪律：

- 每条 case 钉 `input`、期望（或 rubric）、标签；分数必须带 `prompt+model+index+judge` 版本才可比。
- **阈值写死**：例如 Recall@20、schema 率、红线 0 容忍；主指标升但安全掉 = 失败（基础篇护栏）。
- Judge 模型与 judge Prompt 也要版本；换 judge = 重打基线，不能和上周分数直接比。
- 贵的评测异步；失败要可下载 trace，不能只给一个 0.73。
- 坏 case 回流进集（第 6 题），同一失败修复后必须变成 L0/L1 必过。



### Prompt / 索引 / 模型版本：怎么进制品库

三者生命周期不同，**不要绑死成一次 git 提交才能改**，但生产指向必须原子。

| 制品 | 版本怎么钉 | 流水线动作 | 回滚含义 |
| --- | --- | --- | --- |
| **Prompt / 工具 schema / 路由表** | `prompt_id@semver` + git | PR + L0/L1；破坏性 schema = major，和应用解析同发 | 改 `stable` 指向旧 semver |
| **索引** | `index_name@version`（数据快照 + 切分/嵌入模型哈希） | 构建 job：嵌入 → 质量抽样 → 别名切换；蓝绿两份 index | 别名切回旧 version；旧库保留 TTL |
| **基座模型** | 供应商 `model_id` + 日期/区域 | 兼容性评测；tokenizer/上下文长度变更当 breaking | 路由表改回旧 id（第 3 题） |
| **LoRA / FT** | `adapter_id@checkpoint` | 训练独立流水线；推理前加载校验，装错则拒（第 5 题） | 卸适配器或换 checkpoint |
| **护栏 / 词表** | `policy@version` | 安全集 L0 | 切旧 policy |

`experience_id` = 上述指针的冻结组合（或内容哈希）。请求日志只记它，排障才展开。

索引特别点：重建耗时长，CI 里用 **抽样评测 + 异步全量**；切别名才算发布，构建成功 ≠ 上线。嵌入模型一换必须重建，分数不可混比（第 1、4 题）。



### 金丝雀与「体验回滚」

金丝雀对象是 **experience 标签**，不是随机 5% HTTP 各打各的 Prompt。

| 点 | 做法 |
| --- | --- |
| **粘滞** | 按 `session_id` 或 `user_id` 固定 experience，避免中途人格突变 |
| **流量** | 1% → 10% → 50% → 全量；租户可白名单（内部先吃狗粮） |
| **比什么** | 在线：任务成功、转人工、点踩、schema 失败、P95、$/会话、安全事件 |
| **停实验** | 护栏恶化自动停并回滚标签（基础篇 A/B）；不要等「感觉不好」 |
| **长尾** | 金丝雀时间要盖住低频意图；AI 质量问题常不是启动 10 分钟能看完 |

**体验回滚 ≠ 回滚 K8s Deployment**（应用可以没坏）：

1. **秒级**：`prod/stable` 指针改回上一 `experience_id`（Prompt/路由/护栏）。  
2. **分钟级**：索引别名切回；语义缓存按 version 驱逐（第 4 题）。  
3. **不可瞬间**：已训坏的权重、已污染的公共知识库——冻写入、切旧 checkpoint、必要时停定制模型。  
4. **会话中**：已开始的长 Agent run 钉死启动时的 experience，或明确「本轮用旧版收尾」；不要半截换索引。  
5. **业务写**：回滚体验不自动撤销已执行的退款；补偿走业务，不走「再生成一次对不起」。

预发/回放：用同一评测集对 `candidate` vs `stable` 做 pairwise；线上金丝雀是确认分布漂移，不是替代离线门禁。

反模式：只回滚应用镜像但 Prompt 配置中心仍是新版；只回滚 Prompt 但新索引已切；金丝雀按请求随机导致同一用户前后两套人设；评测不过仍靠 feature flag 全量。

### 面试口述（约 50 秒）

> AI 的 CI/CD 在传统镜像流水线之外，交付的是 experience：Prompt、索引、模型、工具和护栏的冻结组合。每条请求打 experience_id，回滚是切标签，不是只回滚一段文案或一次发版。  
> 门禁分层：PR 跑契约和红线小集，贵的 judge 和全量召回放合入前或 nightly；分数必须钉评测与 judge 版本。索引当异步制品，别名切换才算发布。  
> 金丝雀按会话粘滞，盯转人工、schema、安全和成本护栏，恶化就自动切回上一 experience。应用没挂但胡说，也要当成需要回滚的发布事故。

## 第 10 题归档（2026-08-22）

### 不是「开源更省 / 闭源更强」二选一，是四维约束下的路由

自建开源 = 你拥有权重与推理栈（或托管私有端点但仍在你的合规边界内）。  
闭源 API = 买能力与弹性，数据与可用性落在供应商合同里。

一句话：**合规决定能不能出境；效果与延迟决定哪条路够用；成本看稳态用量不是看 token 单价；运维决定你有没有人值班 GPU。** 多数生产是混合，不是信仰站队。



### 四维怎么权衡

#### 1. 合规（通常一票否决）

| 问什么 | 闭源 API | 开源自建 |
| --- | --- | --- |
| **数据驻留 / 出境** | 看区域、是否用于再训练、DPA、日志留存 | 流量可不出业务 VPC；仍要管磁盘、备份、员工访问 |
| **行业资质** | 等保/金工/医疗常要求私有化或专有云 | 更容易满足「数据不出域」，但要自己过审推理环境 |
| **密钥与 Prompt 泄露** | 供应商侧风险 + 你的网关 | 内鬼、训练样本、评测集、GPU 多租户 KV（第 5 题） |
| **开源协议** | 无权重协议问题 | 商用要读 Llama/Qwen 等许可；「开源」≠ 随便商用 |
| **审计** | 依赖对方 SOC2 与你的调用日志 | 全链路你负责：谁能下模型、谁能看对话 |

面试句：合规问的是 **哪份数据、以何种身份、到哪台机器**。闭源不是天然不合规（有专有区域与「不训练」条款）；自建也不是天然安全（运维账号比 API key 更危险）。

#### 2. 成本（不要只比 $/1M token）

闭源：按量清晰，有预留包、缓存折扣、批量；隐形成本是 **封顶难、议价周期、超额 429**。  
自建：显成本是卡、电、机房；隐成本是 **人（推理/值班）、空闲 GPU、扩容失败时的业务损失**。

粗判：

- 流量低、峰值尖、任务难 → API 往往更便宜（你买的是别人的利用率）。
- 流量高且平稳、任务可用中小模型打满 → 自建 TCO 才可能翻盘；要算 **有效 token/秒/卡**，不是标称吞吐。
- 自建「免费模型」仍要付：量化掉点、长上下文 KV、多模态视觉 token、评测与回滚环境（第 9 题）。

和路由（第 3 题）一起算：**平均成本 = 各档份额 × 该档单价**；全走最强闭源和全走 70B 自建都可能是局部最优的幻觉。

#### 3. 效果

| 面 | 闭源 API | 开源自建 |
| --- | --- | --- |
| **通用推理 / 工具 / 长上下文** | 头部模型常领先，迭代快 | 追赶中；垂直域 + RAG/LoRA 可打平具体任务 |
| **可控性** | 约束解码、tool calling 成熟度看供应商 | 可上 vLLM/SGLang、文法约束、自己的 LoRA（基础篇选型） |
| **稳定性** | 模型静默升级会漂（要钉 model 日期） | 你钉 checkpoint；自己负责效果回退 |
| **评测** | 用你的集比，不看榜（第 9 题） | 同样；再加量化/截断是否掉点 |

默认：产品体验用 **同一评测集** 比 API 最强档 vs 自建候选；差在红线内再谈省钱。不要用「开源也能聊天」代替门禁。

#### 4. 运维

| 面 | 闭源 API | 开源自建 |
| --- | --- | --- |
| **弹性** | 对方扩容；你吃 RPM/TPM 配额 | 你扩卡；排队、KV 碎片、批调度 |
| **可用性** | 多供应商 failover（基础篇降级梯子） | 多副本、多区；单机房 GPU 是单点 |
| **发布** | 改 model id 即发版，要防静默变卦 | 镜像 + 权重 + 推理参数进 experience |
| **人员** | 应用工程师 + 网关 | 还要推理/CUDA/容量规划；没有人就不要承诺私有化 SLA |
| **可观测** | 对方黑盒内部；你有网关 span | 可看排队、batch、显存；成本是复杂度 |

一句话：**会叫 API 不等于会跑生产推理；私有化的交付物包含值班手册，不只包含权重文件。**



### 混合部署：边界按「数据面 + 任务面」划，不按「感觉敏感」

混合 = 路由表上的 **安全档 → 端点**（接第 3、5 题），同一套编排、两套或多套后端。

```text
入站鉴权注入 tenant/user
  → 分类：数据敏感级 × 任务类型 × 延迟档
  → 敏感：私有端点（开源或供应商专有云）
  → 通用：公有 API
  → 日志与缓存按端点隔离，禁止敏感 transcript 进公有语义缓存
```

#### 什么必须走私有（默认 fail-closed）

- **明文身份与秘密**：证件、银行卡、病历、未发布财报、客户合同全文、密钥、生物特征。
- **高权限工具上下文**：带内部工单细节去「帮你写退款理由」——工具结果也可能敏感，不能为了效果贴到公有模型。
- **监管点名的字段** 或租户合同写死「不出域」。
- **可反推个人的拼接**：单字段不敏、拼在一起敏 → 按拼接后的最高档。

这些请求：**Prompt、检索片段、tool 回灌、评测抽检** 全部走私有；不得「脱敏一半仍把原文当 few-shot 发给 API」。

#### 什么可以走公有 API

- 无客户数据的通用能力：改写、分类、公域知识、代码草稿（输入已确认无秘）。
- **已脱敏/已聚合** 的统计或占位符模板（「客户A」而不是真名）；脱敏要可逆映射留在你侧。
- 低敏感租户明确同意出境，且合同覆盖再训练/日志条款。

#### 边界怎么工程化（避免人肉每次判断）

| 机制 | 做法 |
| --- | --- |
| **字段级标密** | 业务对象带灵敏度；进窗前扫描 PII；命中则升档或打码 |
| **任务白名单** | 只有声明为 `public_ok` 的 skill 才能出公网；退款/人事默认 private |
| **两端体验对齐** | 私有模型弱时：敏感路径用 RAG + 小模型 + HITL，而不是偷偷送到 GPT「就这一次」 |
| **密钥** | 公有 API key 与私有推理凭证分账；BYOK 按租户（第 5 题） |
| **降级** | 私有挂了：敏感流量 **不能** failover 到公有；只能排队、小模型、拒答或人工（和第 3 题「安全命中不升级绕过」一致） |
| **评测** | 两套后端同一敏感/非敏感切片分别过门禁；混合路由自己也要测「有没有漏送」 |

切分粒度：优先 **请求级**（整段对话一旦出现敏感字段，本 session 钉死私有）。不要同一轮用户话走私有、模型为了好答把摘要再发到公有。

灰色区：嵌入/重排模型、语音 ASR——常被忘记。 **ASR 与 embedding 也是模型调用**，音频和文本一样要分级；别只挡了 LLM 却把病历丢给云端转写。

#### 何时不混合、索性一边倒

- 全敏感、体量中等、有合规期限 → 先私有化最小闭环（小模型 + RAG），效果用 HITL 补。  
- 无敏感、要冲产品、没推理编制 → 全 API + 合同与区域选对，预留网关以便日后拆流。  
- 「混合」若没有分类器和漏送测试，比单边更危险。



### 和其它题的挂钩

- 路由第 3 题：安全档是硬闸；私有/公有是查表结果。  
- 租户第 5 题：有的租户强制私有 endpoint。  
- CI 第 9 题：两套模型都要进 `experience_id`；静默升级公有模型 = 一次未经门禁的发版。

### 面试口述（约 50 秒）

> 开源自建和闭源 API 我按合规、效果、稳态成本、有没有推理运维四维看。数据出不出域往往一票否决；效果用自己的评测集比，不看榜。量小平峰用 API 更划算，量高且中小模型打得过再算 GPU 的 TCO。  
> 生产默认混合：字段和任务标密，敏感请求连同检索和工具回灌都走私有，通用脱敏走 API。私有故障禁止 failover 到公有。ASR、embedding 同样分级。  
> 边界写在路由表和漏送测试里，不写在「我们比较重视隐私」的口号里。没有人值班 GPU 就不要承诺私有化 SLA。
